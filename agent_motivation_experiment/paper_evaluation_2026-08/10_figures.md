# 그림 — 무엇을 주장하고, 무엇으로 그렸고, 무엇을 말하지 않는가

**PDF와 스크립트는 `paper_figures/`에 있다.** 이 파일은 그림마다 **주장 / 데이터 / 캡션에
반드시 들어가야 하는 것**을 적는다. 수치는 스크립트가 출력하는 것이고 여기에 옮겨 적지
않는다 — 옮겨 적으면 재측정 때 한쪽만 갱신된다.

## A2 — `eval_routing_only.pdf` (**EXP-88 대기 중**)

| | |
|---|---|
| **주장** | **아무도 거절하지 않을 때, 요청을 어느 인스턴스로 보낼지 정하는 규칙 하나만으로** 규칙 안에 도착하는 요청 비율이 크게 갈린다 |
| **데이터** | `fsroute`(거절과 보유를 둘 다 끈 FluidServe, **EXP-88** 8 도착률 × 2반복) 대 vLLM router `cache_aware` 대 PolyServe(둘 다 고정 세트, 여덟 도착률 전부 거절률 0.0%) |
| **왜 강한가** | 셋 다 도착한 요청을 전부 받아들이므로 **admission이 비교에서 빠진다.** "너희가 이기는 것은 더 많이 거절해서 아닌가"라는 반론이 이 그림 하나로 닫힌다 |
| **캡션에 반드시** | ① 세 arm의 거절률이 전부 0%라는 것을 수치로 ② **이것이 "라우팅이 admission보다 중요하다"를 뜻하지 않는다**는 것 — 같은 데이터에서 거절을 끄면 25 req/s에서 18.1점을 잃는다 ③ `fsroute`가 여덟 도착률을 한 세션에서 쟀고, 겹치는 세 점이 EXP-78과 대조된다는 것 |

| **말하지 않는 것** | 클래스 선호가 45에서 왜 해로운지의 기제. 측정된 것은 메모리 사유가 3.4% → 18.8%로 오른다는 것까지다 |

## A4 — `eval_oracle.pdf`

| | |
|---|---|
| **주장** | 요청마다 **정확한 출력 길이를 알려 줘도** 네 도착률 전부에서 차이가 사전 문턱 3점 안이고 부호가 두 번 뒤집힌다 |
| **스크립트** | `paper_figures/fig_eval_oracle.py` |
| **데이터** | EXP-64, 4 도착률 × 2 arm × 2반복 = 16조건. 오라클 표 커버리지 99.2%(두 arm 동일) |
| **왜 예측기가 아니라 오라클인가** | 예측기로 하면 음성 결과가 "예측기가 나빠서"일 수 있다. 정답을 주면 **어떤 예측기도 이 축에서 얻을 것이 없다**는 상한이 된다 |
| **검증** | 다시 채점한 값이 EXP-64 §8.1과 같다(−0.3 / −0.2 / +0.6 / −2.0, 반복 폭 3.7/1.8, 3.1/1.1, 4.7/0.9) |
| **캡션에 반드시** | ① 범위가 이 워크로드(chat 77.0%)와 이 판정 조건이라는 것 ② **처리군의 반복 폭이 대조군의 2~5배**라는 것 ③ 오라클을 못 읽으면 워크로드가 종료하므로 "조용히 대조군이 되는" 경로가 막혀 있다는 것 |

## B — `eval_admission_quality.pdf` (**2단 폭 7.0 in**)

| | |
|---|---|
| **주장 (a)** | **배치한 요청의 91~100%를 예산 안에 서비스한다.** 남는 실패는 고르게 퍼지지 않고 deepresearch에 몰리며(35 req/s 위에서 22~34%, chat은 1~4%), **깨지는 규칙이 첫 토큰이지 토큰당 시간이 아니다** |
| **주장 (b)** | **어떤 인스턴스가 목적지에서 탈락할 때 그 이유의 71~98%가 속도 게이트다** — motivation의 중심 문장이 계량된 형태. **KV 메모리는 0%가 아니라 35 req/s 위에서 17~20%다** |
| **스크립트** | `paper_figures/fig_eval_admission_quality.py`, 값은 `eval_b2_feasible_but_missed.py`와 `eval_b1_binding_predicate.py` |
| **데이터** | 고정 세트의 FluidServe 16 run. (a)의 조인 성공률이 **16 run 전부 100.0%** |
| **왜 한 그림인가** | **각각만 보면 반대 결론이 나온다.** (a) 혼자는 전부 거절하는 정책에 만점을 주고, (b) 혼자는 그 거절이 옳았는지 말하지 않는다 |
| **캡션에 반드시** | ① 두 패널의 분모가 다르다는 것 — (a)는 **배치된 요청**, (b)는 **(요청, 인스턴스) 판정 사건** ② (a)에 거절률이 회색 선으로 같이 그려진 이유 ③ (a)의 모집단이 "feasible하다고 판정한 것"이 아니라 "배치한 것"이고 그 차이의 상한이 2.2%p라는 것 ④ **남은 실패에 원인은 있고 처방은 없다** — EXP-87이 바로 그 검사를 판정 조건에 넣었고 대조군 반복 폭 안이었다 |
| **말하지 않는 것** | **거절했는데 사실은 됐을 요청**(false negative)을 재지 않는다. 가장 가까운 것이 EXP-78의 거절 끈 arm이고, 거기서는 받아들인 것 중 지킨 비율이 89.8% → 56.2%로 내려간다 |

## B3 — `eval_pace_diversity.pdf`

| | |
|---|---|
| **주장** | **함대가 제공할 수 있는 서로 다른 토큰당 속도의 개수가 부하가 아니라 클래스 배치로 정해진다** — 세 개(10~20 req/s) → 하나(25 req/s) → 두 개(35~70 req/s). 두 개일 때 느슨한 쪽은 **인스턴스 하나**다 |
| **스크립트** | `paper_figures/fig_eval_pace_diversity.py`, 값은 `eval_load_is_not_capacity.py` |
| **데이터** | 고정 세트의 FluidServe 16 run, run마다 485~552 스크레이프의 인스턴스별 `gate_allowance_ms` |
| **왜 중요한가** | 이 그림이 B1과 B2를 잇는다. 게이트가 탈락 사유의 대부분이고(B1), 그 게이트가 함대를 접고(이 그림), 접힌 결과 deepresearch가 갈 곳이 하나뿐이라 그 클래스의 22~34%가 첫 토큰 예산을 넘긴다(B2) |
| **캡션에 반드시** | ① 이것은 **우리 정책의 시야**이지 정책 간 비교가 아니라는 것 ② `-1`(요청 없음)을 속도 개수에서 뺐다는 것 ③ 막대가 시간 평균이지 한 순간이 아니라는 것 ④ **35~70 req/s의 100 ms 약 22%가 엔진 넷 중 한 대**라는 것 |
| **말하지 않는 것** | 25 req/s의 붕괴가 왜 그 도착률에서만 일어나는지. 그 지점이 거절이 처음 시작되는 곳(1.9%)이고 `overIncumbents` 사유가 17.4%로 튀는 곳이라는 것까지가 관찰이다 |
| ⚠ | **같은 스크립트의 첫 표는 우리에게 불리하게 읽힐 수 있다** — 부하 인식 라우터의 선택이 가장 느슨한 인스턴스를 놓치는 비율이 저부하 85~97%, 고부하 5~13%다. **그 자체로 인용하면 "고부하에서는 부하로 골라도 된다"가 되므로, 반드시 두 번째 표(고를 것이 없어진다)와 같이 적는다** |

## A5 — `eval_per_class.pdf` (**2단 폭 7.0 in, 패널 셋**)

| | |
|---|---|
| **주장** | 총계 하나가 서로 반대인 사실 둘을 가린다. **chat(요청의 76.9%)에서 크게 이기고, deepresearch는 45 req/s부터, agent는 25 req/s부터 진다** |
| **스크립트** | `paper_figures/fig_eval_per_class.py` |
| **데이터** | 고정 세트 5 arm × 8 도착률 × 2반복 = 80 run |
| **왜 논문에 넣는가** | *"특정 클래스를 버려서 이기는 것 아닌가"*가 심사에서 반드시 나온다. **이 그림이 그 질문에 정면으로 답하고**, 지는 칸의 원인이 B2·B3로 이미 측정돼 있다 |
| **캡션에 반드시** | ① **llm-d 외의 세 기준선은 25 req/s 위에서 무너지므로** 그 구간의 곡선은 정책의 선호가 아니라 작동을 멈춘 시스템이다 ② Llumnix SLO와 llm-d가 m1f 설정을 받지만 **채점은 어느 arm이든 agent를 전체 시간 30초로 한다**는 것 ③ llm-d의 10 req/s 반복 폭 11.5점 |
| ⚠ 같이 적어야 하는 것 | **agent 클래스에서 다섯 중 1위는 PolyServe다**(25~45 req/s에서 98.3 / 92.1 / 58.2). 같은 구간 그 정책의 chat은 4.2~0.3%다. **정적 격리가 지켜 주는 클래스와 그 대가가 같은 표에 있다** — discussion에 그대로 쓴다 |
