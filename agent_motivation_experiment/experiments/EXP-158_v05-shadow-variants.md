# EXP-158: v0.5 위에서 판정 변형을 같은 상태로 다시 계산하기 (shadow)

**날짜**: 2026-11-12 (실행 전 작성)
**질문**: v0.5의 판정에서 horizon을 빼고 budget 기준으로 바꾸면, 같은 상태에서 결정이 어떻게 달라지는가. 그 변경이 받아도 됐을 요청을 거절하게 만드는가, v0.5가 거절한 요청을 받게 만드는가,
그리고 클래스 분리를 깨는 결정(chat 인스턴스는 모두 불가인데 다른 인스턴스는 가능)을 늘리는가.

## 배경

- EXP-157: v0.6-후보2(v0.5 + 정점 KV 예측 + 판정 분리 + budget 여유 기준 판정선 + KV 한도 0.98)는 v0.5보다 모든 도착 기준 12점 낮았다. 원인은 서로 맞물린 세 가지였다
  — 토큰당 시간 판정이 처리 중 요청들에게 budget 여유를 쓰게 허용해 최소 여유가 작아지고, prefill 간섭 지연 시험이 그 최소 여유로 새 요청을 막았다; KV 예측의 오차 여유(1.65 × 오차)가 한도 증가분보다 컸다;
  chat 인스턴스가 막힌 순간 새 chat 자신의 허용치(첫 토큰에서 남긴 TTFT budget을 토큰당 시간으로 환산한 것)로 다른 인스턴스에 들어갈 수 있게 되어 클래스 분리가 풀렸다.
- 그래서 v0.5에서 다시 출발한다(2026-11-12 사용자 결정). 클래스 분리는 판정선의 부수 효과로 두되 매 실험에서 판정 기준으로 확인한다.
- v0.5에서 h가 판정에 들어가는 곳은 둘이다: ① 평균 iteration 시간 = decode 시간 + prefill 간섭 지연 ÷ h(그리고 대기 prefill 추정 = max(지금 대기, h × iteration 시간 동안 도착할 prefill)),
  ② pend/거절에 쓰는 TTFT 예측의 같은 대기 prefill 추정. KV 투영 끝점도 h에 따라 낙관적이다(EXP-155: 끝점 −0.5 % at h25 → −15.9 % at h200).

용어: **budget 여유** = 지금 만들어야 할 토큰의 마감(도착 + TTFT budget + j × TBT budget)까지 남은 시간. **prefill 간섭 지연** = prefill chunk가 iteration을 길게 만들어 decode 중인 요청의 다음 토큰이 늦어지는 시간.

## 기록하는 것

- 후보 단위: 변형마다 가능/불가. 실제 판정에서 같이 걸린 조건의 조합(`scheduler_fluidserve_infeasible_mask_total{tier,mask}`).
- 결정 단위(`scheduler_fluidserve_shadowv_*`): 변형마다 "가능한 인스턴스가 있었는가"의 실제 대비 뒤집힘(방향별), 고른 인스턴스가 달라졌는가,
  **분리 기회**: 그 클래스가 이미 있는 인스턴스는 모두 불가인데 그 클래스가 없는 인스턴스는 가능한 결정 수(클래스별). T는 pend ↔ shed 뒤집힘.
- 요청 단위(결정 로그 `fsshadowv` 줄, route·shed 때 한 줄): 시도 횟수, 변형마다 처음 가능했던 시각(기다린 ms, 없으면 −1), 마지막 시도에서 변형마다 가능했는가, T였다면 pend였는가.
- 분리 지표(실제 run): chat이 있는 인스턴스 수(gauge `gate_allowance_ms` ≤ 50)의 시간 평균과 3대 이상 비율, chat이 chat 없는 인스턴스로 간 횟수, chat 보유 구간 수, chat이 chat 위주 두 대에 들어간 비율.
