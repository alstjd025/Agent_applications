# EXP-152 — prefill 비중의 분모를 줄이면 왜 좋아지나: 예측이 정확해져서인가, 배분이 바뀌어서인가 (기존 데이터 분석, GPU 없음)

작성 2026-11-08. 사용자와 합의한 계획(2026-11-08 대화): 1단계 정확도, 2단계 배분. 새 run은 없고 EXP-151의 여섯 run을 쓴다.
스크립트: `analysis_scripts/exp152/` (`pace_accuracy.py`, `slack.py`, `alloc.py`, `where.py`).

## 질문

EXP-151에서 horizon 100에 토큰당 시간 추정의 분모만 25·50으로 바꾸면 모든 도착이 5.9~6.1점 올랐다. 그런데 대조(분모 100)도 받아들인 요청은 이미 99.96 %
마감을 지켰다. 그러면 이득은 (가) 예측이 실제에 가까워져서인가, (나) 긴 프롬프트를 비싸게 보는 것이 배분을 바꿔서인가.

## 1단계: 분모별 예측이 실제 iteration 시간에 얼마나 맞나

방법: 스케줄러가 1초마다 기록한 인스턴스별 상태(decode 모델 값, 보정값, 대기 prefill, prefill duty, 지금 토큰당 시간)로 `meanStepMs`를 분모 25·50·100에 대해
다시 계산하고, 그 시각 뒤 25·50·100 iteration 동안 실제로 걸린 평균 iteration 시간(상태를 받을 때마다 잰 시간 차이 ÷ step 수 차이, step 수로 가중)과 비교했다.
재계산은 기록된 예측값과 일치한다(차이 중앙값 0.001 ms, 대조 run 14,412 표본, p50 run 14,251 표본).

| 비교 창 | 분모 25 | 분모 50 | 분모 100 |
|---|---|---|---|
| 다음 50 iteration, 예측/실제 중앙값 (대조 run) | 1.017 | 1.008 | 1.007 |
| 다음 100 iteration, 예측/실제 중앙값 (대조 run) | 1.010 | 1.004 | 1.004 |
| 다음 50 iteration, 예측/실제 중앙값 (p50 run) | 1.018 | 1.018 | 1.018 |

- **지금 상태의 예측은 분모와 거의 관계가 없다**(중앙값 차이 1 % 이하). 이유: 도착할 prefill의 예상량이 `duty × (h × 지금 토큰당 시간)`이라서 h에 비례하고, 그것을 다시 h로
  나누므로 h가 약분된다. h가 남는 것은 대기 prefill이 실제로 쌓여 있는 순간뿐이고, 그때도 차이는 작다(swe가 가장 빡빡한 인스턴스에서 평균 오차 분모 25 −10.3 ms, 100 −17.4 ms).
- 중앙값은 맞지만 평균은 실제보다 작게 예측한다(다음 50 iteration 평균 오차 −11 ms 안팎). prefill이 낀 긴 iteration이 평균을 끌어올리는데, 이것은 분모와 관계없이 남는다.
- 따라서 분모가 결정을 바꾸는 곳은 **새 요청을 넣은 뒤의 예측**이다. 넣을 요청의 프롬프트(8,192 토큰 이하면 1청크)가 1/h 비중으로 더해지므로, deepresearch(3.8K, prefill
  한 번 약 230 ms)는 분모 100이면 평균에 +2.3 ms, 25면 +9.2 ms를 더한다. 이것은 "더 정확한 값"을 고르는 문제가 아니라 **그 지연을 몇 iteration에 나눠 볼 것인가**라는 선택이다.

## 2단계: 배분

(가) 처리 중인 요청의 실제 여유. ladder95에서 토큰 i의 마감은 TTFT 예산 + i × 토큰당 예산이므로, 첫 토큰을 빨리 받은 요청은 남은 TTFT 예산만큼 여유를 계속 들고 간다.
클라이언트 토큰 기록으로 잰 slack(마감 − 실제 도착)은 대조 run(r1)에서:

| 클래스 | 수명 중 최소 slack p1 | p5 | 중앙값 |
|---|---|---|---|
| chat | 2,711 ms | 3,393 ms | 4,480 ms |
| deepresearch | 2,635 ms | 4,496 ms | 8,167 ms |
| swe | 1,099 ms | 2,546 ms | 5,052 ms |

chat 요청의 99 %는 수명 내내 2.7초 이상 여유가 있다. deepresearch prefill 한 번(약 230 ms)이나 swe prefill 한 번(6.4K, 약 390 ms)은 그 안에 들어간다. 즉 지금의 판정
(chat이 있는 인스턴스는 넣은 뒤 평균 iteration 시간이 45 ms(50 × 0.9) 이하여야 한다)은 **ladder95 기준으로는 처리 중인 chat의 마감을 지키는 데 필요한 것보다 훨씬 엄격하다.**
(이 여유는 지금 정책이 만든 상태에서 잰 것이다. 판정을 풀면 부하가 늘어 여유가 줄어든다. 또 이 결론은 누적 마감 규칙(ladder95)에서만 성립하고, 토큰 사이 간격 하나하나를
보는 규칙이라면 다르다.)

(나) 인스턴스 배분: 5분 창마다 허용 속도 50 ms(chat 있음)·75 ms·100 ms인 인스턴스 수를 세면 대조·p50·p25가 **창마다 거의 같다**(예: 15~30분 창 셋 모두 1.0/3.0/0.0,
50~55분 창 셋 모두 2.0/2.0/0.0). 그런데 같은 창에서 chat 거절은 크게 다르다(20~25분: 대조 42 %, p50 22 %, p25 18 %; 50~55분: 38 %, 20 %, 16 %).
즉 차이는 "chat 인스턴스가 몇 개냐"가 아니라 **chat 인스턴스 안에서** 생긴다.

(다) 어디로 route됐나(route 순간 그 인스턴스의 허용 속도로 분류, 반복 1 / 반복 2):

| | 대조 | p50 | p25 |
|---|---|---|---|
| deepresearch route 중 chat 인스턴스로 간 비율 | 19.7 % / 23.2 % | 14.8 % / 15.1 % | 7.6 % / 7.9 % |
| swe route 중 chat 인스턴스로 간 비율 | 27.1 % / 29.7 % | 18.1 % / 17.5 % | 11.8 % / 9.8 % |
| chat 인스턴스로 간 deepresearch+swe 프롬프트 합 | 25.0M / 28.5M 토큰 | 18.2M / 18.1M | 11.9M / 10.7M |
| deepresearch route 중 deepresearch만 있는 인스턴스로 간 비율 | 3.4 % / 9.6 % | 6.1 % / 7.4 % | 17.1 % / 18.5 % |

분모를 줄이면 긴 프롬프트가 chat 인스턴스로 가는 양이 절반 이하로 준다(25.0M → 11.9M 토큰). chat 인스턴스는 대기 prefill과 KV가 적은 상태로 남고, 그 상태에서 새 chat이
판정을 통과한다(chat 거절 20.4 % → 14.3 %). deepresearch는 chat 인스턴스에서 밀려나 swe·deepresearch 인스턴스로 가거나 거절된다(p25에서 거절 30.5 → 37.3 %).

## 결론

**(나) 배분이다.** 분모는 지금 상태의 토큰당 시간 예측을 거의 바꾸지 않고(1단계), 처리 중인 요청의 마감 보호에도 필요하지 않았다(대조에서도 admitted 99.96 %, chat 여유
p1 2.7초). 바뀌는 것은 **긴 프롬프트를 chat 인스턴스에 넣을 때 매기는 값**이고, 그 값이 클래스를 인스턴스별로 나누는 정도를 정한다. 분모 25·50이 좋은 것은 예측이 정확해서가
아니라 chat 인스턴스에서 긴 프롬프트를 더 강하게 밀어내기 때문이다.

그래서 식을 "더 정확한 분모"로 고치는 것은 목표가 맞지 않는다. 다음 설계 후보:
1. **처리 중인 요청 보호를 ladder 여유로 판정**: "넣은 뒤 평균 iteration 시간 ≤ 45 ms" 대신 "넣으면 생기는 지연(prefill 시간 − decode step) ≤ 그 인스턴스 처리 중 요청들의
   최소 slack"으로. 마감을 지키는 데 필요한 만큼만 막는다.
2. **chat 인스턴스의 용량을 무엇에 쓸지 직접 정하는 규칙**: 긴 프롬프트를 chat 인스턴스에 넣으면 그 뒤 들어올 chat이 받는 손해(새 chat의 판정 통과율)를 값으로 매기거나,
   chat 인스턴스에 들어갈 수 있는 prefill 양에 상한을 둔다. 지금은 분모 하나가 이 역할을 우연히 하고 있다.
3. 둘을 shadow 판정으로 같은 상태에서 먼저 비교하고, 가장 나은 것을 한 시간 trace로 A/B한다.

논문 서술에 대한 함의: 그림 15의 horizon 효과를 "예측 기간이 길어 불확실하다"로 설명하는 것도, "분모를 줄이면 예측이 정확해진다"로 설명하는 것도 측정과 맞지 않다. 측정이
보여 주는 것은 "긴 프롬프트를 chat 인스턴스에 넣는 값을 얼마로 매기느냐가 클래스 분리 정도를 정하고, 이 워크로드에서는 강하게 분리할수록 전체 점수가 오르고
deepresearch가 손해를 본다"이다.
