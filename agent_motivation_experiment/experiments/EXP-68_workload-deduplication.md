# EXP-68 — 워커별 프롬프트 중복을 없앤 워크로드에서 다시 잰다

**상태**: 워크로드 수정 적용 완료(`0cef289`), **3분 smoke 검증 중**, 본 실험 미실행.
**결정 자료**: [`ms_dev/notes/workload-decision.md`](../../../ms_dev/notes/workload-decision.md).
결함의 발견과 크기는 [`fluidserve-prefix.md`](../../../ms_dev/notes/fluidserve-prefix.md) §8.

## 1. 무엇을 고쳤나

`run_experiment.py:_worker_main`이 워커별로 데이터셋을 나누는 줄을 갖고 있고 주석에 이유까지
적혀 있는데(*"Disjoint-ish slice per worker so streams differ (reduces exact-duplicate
prefix-cache masking)"*), 조건이 `isinstance(dataset, list)`이고 mixed 워크로드의
`load_dataset`은 dict를 돌려주므로 **한 번도 실행된 적이 없다.**

측정된 결과: **모든 프롬프트가 정확히 12.00번씩** 나갔고, 사본 12개가 **2.1초 안에**,
연속 사본은 **0.11초** 간격으로 도착했다(99.9%가 1초 이내).

| 고친 것 | 어디 |
|---|---|
| 클래스별 리스트를 워커 조각으로 자른다. **자랐는지 안 잘랐는지를 매번 출력한다** | `mixed_request_level_poisson/workload.py` `create_task_pool` |
| `num_conversations` 1,000 → **10,000** | `mix_short_m1_balanced.json`, `mix_short_m1_slofair.json` |

10,000인 이유: 70 req/s에서 chat이 25,896건을 뽑는데 10,000 대화가 약 33,540건을 주므로
워커당 조각 2,795건 대 뽑는 양 2,158건이 되어 **한 바퀴도 안 돈다.** 8,000이면 1.04배로
아슬아슬하다. 표본은 **고정 시드로 섞은 뒤 앞에서 N개**라 1,000 집합이 10,000 집합의
앞부분이고 앞 1,000개의 task id도 그대로다.

## 2. 무엇이 달라지나 — 계산

### 정적 70 req/s (8분)

| 클래스 | 풀(요청) | 지금 | 분할만 | **분할 + chat 10,000** |
|---|---|---|---|---|
| chat | 3,354 → 33,540 | 12회 / 0.18초 | 7.7회 / 62초 | **1회 (반복 없음)** |
| deepresearch | 60,000 | 12회 / 0.18초 | **1회** | 1회 |
| swe | 1,500 | 12회 / 0.18초 | 1.7회 / **279초** | 1.7회 / 279초 |

swe만 1.7회 남는데 간격이 279초라 엔진 캐시가 그 사이에 대부분 축출된다.

### 한 시간 trace — **아직 안 고쳐졌다**

도착 181,733건(chat 142,067 / dr 21,512 / swe 18,154).

| 클래스 | 필요 | 지금 | 판정 |
|---|---|---|---|
| deepresearch | 21,512 | 60,000 | 충분 |
| chat | 142,067 | 33,540 | **42,357 대화 필요** |
| **swe** | **18,154** | **1,500** | **short7k transcript가 1,500건뿐이다** |

swe가 진짜 제약이다. `transcript_swe_calls.jsonl`에 13,218건이 있지만 short7k로 줄이기 전
원본이라 **프롬프트 길이 분포가 다르다** — 그걸 쓰면 워크로드를 두 군데 바꾸는 셈이 된다.
**short7k 기준으로 18,000건 이상을 새로 만드는 것이 별도 작업으로 남아 있다.**

## 3. smoke가 확인할 것 셋 (조건을 걸기 전에)

1. `[mixed] shard k/12: class 'chat' -> N` 줄이 워커 12개에서 찍히는가
2. **`task_id` 중복이 12.00 → 1에 가까워지는가**
3. 10,000 대화가 메모리·로딩 시간에 문제를 만들지 않는가

검증 명령:

```bash
python3 - <<'EOF'
import pandas as pd
r = pd.read_csv("<run>/metrics.csv", low_memory=False)
r = r[r.agent != "job_summary"]
print(len(r) / r.task_id.nunique())   # 12.00이었다. 1에 가까워야 한다
EOF
```

## 4. 본 실험 — 아직 안 걸었다

**권고**: FluidServe(대조) · fspfx(prefix 인식) · llm-d × 45/55/70 req/s × 2반복
= **18조건, 약 6.5시간.**

⚠ **워크로드가 바뀌었으므로 EXP-53·57·66·67의 값과 나란히 놓을 수 없다.** llm-d를 다시 재는
것이 선택이 아니라 필수인 이유가 이것이다 — 그 arm의 이점이 바로 prefix 재사용에서 왔다.

## 5. 실행 전에 적는 판정 규칙

| # | 예상 | 무엇이 나오면 틀린 것인가 |
|---|---|---|
| H1 | 엔진 prefix hit rate가 세 arm 전부 **내려간다**. deepresearch는 약 20%, swe는 약 84%가 상한 | 안 내려가면 수정이 결정 경로에 도달하지 못한 것이다 |
| H2 | **llm-d의 우위가 줄어든다** — EXP-66에서 50~60 req/s의 +9.7~13.0이 좁혀진다 | 안 줄면 그 우위의 원인이 prefix 재사용이 아니었다는 뜻이고, `llmd-baseline.md` §9.11을 철회해야 한다 |
| H3 | **우리 prefix 인식의 이득도 줄어든다** — EXP-67의 +11.0/+7.8/+2.6이 작아진다 | 안 줄면 그 이득이 재사용이 아닌 다른 것에서 온 것이다 |
| H4 | **task당 유효 엔진 수가 두 arm에서 처음으로 갈라진다** | 안 갈라지면 순위에 prefix가 없다는 §5의 한계가 워크로드와 무관하게 구속력을 갖는 것이고, 그때는 `fluidserve-prefix.md` §9(capKv 일관성 수정)가 다음 수다 |

**H2와 H3가 반대 방향이고 어느 쪽이 큰지 모른다는 것이 이 실험의 요점이다.**
`workload-decision.md` §3에 세 힘이 두 방향이라고 적어 둔 그대로다.

## 6. 같은 단계에서 하지 않기로 한 것

- **믹스 비율(10:2:1)** — 결함이 아니라 설계 선택이다. 워크로드와 믹스를 같은 단계에서
  바꾸면 둘을 구별할 수 없다.
- **swe의 공통 시스템 프롬프트 줄이기** — 사용자가 말한 "agent 약 60%"에 닿으려면 이것이
  필요하다(재생을 0으로 만들어도 구조적 공유만으로 73.2%). 그런데 그것은 워크로드의 **의미**를
  바꾸는 것이라 별도 결정으로 남긴다.
- **한 시간 trace** — swe transcript를 새로 만들어야 한다(§2).
