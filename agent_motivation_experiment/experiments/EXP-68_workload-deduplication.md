# EXP-68 — 워커별 프롬프트 중복을 없앤 워크로드에서 다시 잰다

**상태**: 워크로드 수정 적용·smoke 검증 완료(`0cef289`). **70 req/s 첫 탐침 실행 중**(§4).
전체 범위는 미실행(§5).
**결정 자료**: [`ms_dev/notes/workload-decision.md`](../../../ms_dev/notes/workload-decision.md).
결함의 발견과 크기는 [`fluidserve-prefix.md`](../../../ms_dev/notes/fluidserve-prefix.md) §8.

## 1. 무엇을 고쳤나

`run_experiment.py:_worker_main`이 워커별로 데이터셋을 나누는 줄을 갖고 있고 주석에 이유까지
적혀 있는데(*"Disjoint-ish slice per worker so streams differ (reduces exact-duplicate
prefix-cache masking)"*), 조건이 `isinstance(dataset, list)`이고 mixed 워크로드의
`load_dataset`은 dict를 돌려주므로 **한 번도 실행된 적이 없다.**

측정된 결과: **모든 프롬프트가 정확히 12.00번씩** 나갔고, 사본 12개가 **2.1초 안에**,
연속 사본은 **0.11초** 간격으로 도착했다(99.9%가 1초 이내).

| 고친 것 | 어디 |
|---|---|
| 클래스별 리스트를 워커 조각으로 자른다. **자랐는지 안 잘랐는지를 매번 출력한다** | `mixed_request_level_poisson/workload.py` `create_task_pool` |
| `num_conversations` 1,000 → **10,000** | `mix_short_m1_balanced.json`, `mix_short_m1_slofair.json` |

10,000인 이유: 70 req/s에서 chat이 25,896건을 뽑는데 10,000 대화가 약 33,540건을 주므로
워커당 조각 2,795건 대 뽑는 양 2,158건이 되어 **한 바퀴도 안 돈다.** 8,000이면 1.04배로
아슬아슬하다. 표본은 **고정 시드로 섞은 뒤 앞에서 N개**라 1,000 집합이 10,000 집합의
앞부분이고 앞 1,000개의 task id도 그대로다.

### 8.1 기제 — llm-d가 짧은 클래스를 잘라내고 엔진을 prefill로 채운다

클래스별 거절률(반복 1):

| req/s | | chat | deepresearch | swe |
|---|---|---|---|---|
| 35 | fspfx | 10.6% | 22.9% | 54.3% |
| | llm-d | **43.2%** | 52.9% | 47.7% |
| 45 | fspfx | 33.7% | 25.8% | 73.2% |
| | llm-d | **77.7%** | 49.1% | 40.8% |
| 55 | fspfx | 45.3% | 33.5% | 78.1% |
| | llm-d | **87.4%** | 46.0% | 58.9% |

**llm-d는 chat을 55 req/s에서 87.4% 거절한다.** chat은 요청 수의 76.9%를 차지하면서
입력이 평균 677 토큰으로 가장 짧은 클래스다. 짧은 것을 잘라내고 긴 것(deepresearch
4,534 토큰, swe 6,582 토큰)을 남기면 **엔진이 계산하는 일의 구성이 prefill 쪽으로
기운다.** 엔진이 보고하는 값이 그것을 그대로 보여준다:

| req/s | | 엔진 prefix hit | prompt 토큰/초 | **생성 토큰/초** | preemption |
|---|---|---|---|---|---|
| 35 | fspfx | 38.7% | 40,370 | **14,279** | 0 |
| | llm-d | 37.7% | 33,066 | 9,427 | 0 |
| 45 | fspfx | 22.5% | 39,774 | **14,384** | 256 |
| | llm-d | 33.7% | 37,667 | 7,597 | 39 |
| 55 | fspfx | 23.2% | 40,417 | **15,034** | 317 |
| | llm-d | 38.9% | 34,157 | 7,647 | 0 |

**prompt 토큰은 두 arm이 비슷한데(33~40k/초) 생성 토큰은 우리가 1.5~2.0배다.** 즉 llm-d는
요청의 78.8%를 거절하고도 엔진의 prefill 부담을 우리만큼 지고 있으면서 그 대가로 나오는
디코드 토큰이 절반이다. token goodput 차이(+89~94%)가 이 표에서 그대로 유도된다.

### 8.2 판정 규칙에 대한 답

- **H1 통과** — 엔진 prefix hit rate가 두 arm 다 내려갔다. 수정 전 llm-d 93.5% / FluidServe
  75.1%였던 것이 **37.7~38.9% / 22.5~38.7%**다. 수정이 결정 경로에 도달했다.
- **H2 통과** — llm-d의 우위가 줄어든 정도가 아니라 **부호가 바뀌었다.** 수정 전 EXP-66에서
  45/55 req/s가 +0.2 / +13.0이었는데 지금은 **−8.0 / −7.5**다(부호는 llm-d 기준).
  `llmd-baseline.md` §9.11(llm-d의 우위가 prefix 재사용에서 왔다)이 확증됐고 철회할 것이 없다.
- **H3** — 대조군 `fluidserve`를 새 워크로드에서 재지 않아 **답할 수 없다.** prefix 인식의
  이득이 얼마나 남았는지는 조건 6개를 더 돌려야 한다(§9).
- **H4** — task당 유효 엔진 수는 아직 계산하지 않았다. 반복 2가 끝난 뒤 두 반복으로 낸다.

### 8.3 이 표를 읽을 때 같이 봐야 하는 것 넷

1. **반복 1회다.** 이 저장소의 규칙은 조건당 1회로 판정하지 않는 것이고, EXP-66에서
   llm-d의 반복 간 폭이 60 req/s에서 11.7점이었다. 반복 2를 기다린다.
2. **EXP-66과 나란히 놓을 수 없다.** 워크로드가 2026-08-08 11:00에 바뀌었다. 절대값이
   양쪽 다 무너진 것(35 req/s에서 우리 100.0 → 64.9)은 정책이 나빠진 것이 아니라
   프롬프트 재생이 사라져 엔진이 실제로 계산해야 하는 prefill이 늘어난 것이다.
3. **swe의 SLO 분해가 arm마다 다르다** — 우리는 m1 + `25:e2e:30000`, llm-d는 m1f의
   2,500/52다. swe는 llm-d가 유리한 유일한 클래스인데(35 req/s에서 거절 47.7% 대 우리
   54.3%) 그 클래스가 두 arm이 다른 예산을 받는 클래스다.
4. **llm-d 클라이언트는 거절을 `is_rejected`와 `is_error`에 둘 다 세운다.** 채점표의
   `rej`와 `err` 열이 같은 요청을 두 번 보고하는 것이고 점수는 OR이라 영향이 없다.
   진짜 오류는 세 조건 합쳐 `400 Bad Request` 2건뿐이다.

**부분 완료로 잘린 요청(cutoff)이 두 arm에서 비대칭이라 감도를 재 봤다.** 이것들은 결과가
정해지지 않았으므로 양쪽 분모에서 빠지는데, 우리 쪽이 1.6~2.0%로 llm-d의 0.5~1.2%보다
많다. **전부 실패로 세는 최악의 경우에도 우위가 유지된다**: +17.1/+8.0/+7.5 → **+16.0 /
+7.1 / +6.8점.**

### 8.4 무릎이 어디로 갔나

수정 전에는 45 req/s가 교차점이었고 35 이하에서 우리가 100.0이었다. **지금은 35에서 이미
64.9이므로 무릎이 35보다 아래로 내려갔다.** 세 rate가 전부 무릎 오른쪽이라 이 sweep은
"포화에서 누가 더 잘 버티는가"를 재고 있고 "무릎이 정확히 어디인가"는 재지 않는다.
그것을 알려면 **25 req/s 이하를 추가로 재야 한다**(§9).
