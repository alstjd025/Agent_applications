## D0 — 진단: 후보 3 + 지금 점유량 기준 메모리 판정 (arm `fsxc3lvl`, 바이너리 `5d52124e`, 코드 변경 없음)

## P1 — 후보 3 + 가격의 부족도를 받는 판정의 상한(0.95 × pool) 기준으로 (arm `fsxc3plim`, 바이너리 `scheduler-exp177-plimit` `b4c44267`, 브랜치 `exp177-price-limit` `764186f`)

**바꾸는 것 하나(후보 3 대비)**: KV 가격의 부족도 u = (물리 KV + 대기 prefill) ÷ **pool** → ÷ **(memory safety 0.95 × pool)** (`--fluidserve-kv-price=limit`).
가격은 점유가 받는 판정의 상한에 닿으면 켜지고(엔진이 preemption하기 전), 그 뒤 동작(처음값, 곱셈 갱신, λ·c ≤ 1, 동점 정렬)은 후보 3과 같다. 새 상수 없음(0.95는 기존 값).
메모리 판정은 후보 3 그대로(h step 끝점 예측)이므로 넘침의 원인은 남는다 — 이 arm은 "가격이 일찍 켜지면 넘침과 preemption이 줄고 받은 요청의 마감이 지켜지는가"를 묻는다.
에이전트 ⑤(리뷰어 관점)가 오늘 밤 1순위로 꼽은 안이기도 하다(위험 R5: 후보 3의 admitted 95.90·preemption 51k가 논문의 "많이 받고 많이 어긴다" 비판과 같은 모양).

**예측과 판정 규칙(실행 전)**: preemption이 후보 3(약 51k)보다 줄고, admitted가 오르며(목표 99 이상), 모든 도착은 후보 3과 문턱(4.6) 안. 
반증: admitted가 후보 3과 문턱(1점) 안이면 일찍 켜진 가격이 넘침을 막지 못한 것이다. 모든 도착이 9.2점 넘게 낮으면(약 75 미만) 1회로 탈락.
가격이 혼자 막은 평가 수는 후보 3보다 많아야 한다(가격이 더 자주 켜지므로) — 그렇지 않으면 구현이 의도대로 동작하지 않은 것이다.

## A — 하나의 물리 KV stock을 메모리 판정과 가격이 같이 읽는다 (arm `fsxstock`, 바이너리 `scheduler-exp177-stock` `1b89579b`, 브랜치 `exp177-kv-stock` `39286c5`)

에이전트 ①(생존함수·유량 유지)의 1순위 후보이고, ③(통합)의 D3·⑤(리뷰어)의 1순위와 같은 방향(가격을 넘침이 아니라 충족되지 못한 수요로 올린다)이다.
**회계 규칙**: 어떤 결정도 아직 일어나지 않은 유출을 미리 빼지 않고, 앞으로의 도착도 세지 않는다(둘 다 같은 양을 여러 결정이 두 번 세게 만든다).
- 메모리 판정: 물리 KV + 아직 계산되지 않은 prefill(엔진 대기·prefill 중·보냈지만 보고 전) + 이 요청의 prompt − prefix 적중 ≤ pool. 0.95, z, h가 메모리 판정에서 빠진다. 속도에서 나온 capKv는 그대로.
- 가격(후보 3의 식 그대로): 부족도 u = (위 stock + 직전 엔진 상태 구간에서 이 인스턴스가 **메모리 조건 하나 때문에** 불가였고 결국 pend 또는 reject된 요청들의 prompt − prefix 적중, 요청마다 한 번) ÷ pool.
- 새 상수 없음. 단순화: 엔진 상태 사이의 성장분(약 0.25 %/500 ms)과 드문 "곡선이 지금보다 나중에 높아지는" 경우의 상승분은 넣지 않았다.
후보 3 대비 두 가지(메모리 판정, 가격 신호)가 같이 바뀐다 — 각각의 몫은 D0(메모리 쪽만)과 P1(가격 기준만)이 따로 잰다.

**예측과 판정 규칙(실행 전, 에이전트 ①의 예측을 그대로 쓴다)**: preemption 8k~20k, admitted 97.4~99.0, 모든 도착 80~87, chat 거절률 8 % 이하, deepresearch 거절률 35~42 %, goodput 81,880 ± 5 %, 엔진 KV 평균 0.80 ± 0.03.

절반 넘게 줄었는데 admitted 증가 < 1(admitted 손실의 원인이 preemption이 아니다), R4 KV 평균이 0.05 넘게 줄고 모든 도착도 떨어진다(대기 prefill을 지금 점유로 세는 것이 지나치게 보수적이다).
모든 도착이 9.2점 넘게 낮으면 1회로 탈락.

## D3 — A + GPU 시간 가격 (arm `fsxdual`, 바이너리 `scheduler-exp177-dual` `1de94045`, 브랜치 `exp177-dual` `3ba37e7`)

에이전트 ③(통합)의 D3와 ②(예측 버림)의 후보 2가 같은 것을 다른 형태로 제안했다: 인스턴스의 두 용량(KV, GPU 시간)에 각각 값을 두고, 수요가 용량을 넘을 때
"요청 하나가 그 용량을 얼마나 쓰는가"로 누구를 받을지 정한다. affinity는 따로 있는 규칙이 아니라 "빡빡한 요청이 모든 처리 중 요청에게 지우는 고정 비용"으로 사용량에 들어간다.
**바꾸는 것 하나(A 대비)**: 인스턴스마다 두 번째 가격 μ를 둔다.
- 요청의 GPU 시간 사용량 a = prefill 작업(chunk 수 × (t_pre − c0)) + corr × (c_n × E[L] + c_kv × c) + corr × c0 × E[L] × (1 − B_q ÷ B_min)⁺ (ms, B_min은 처리 중 요청들의 명목 budget 최솟값).
- 부족도 s = (평균 iteration 시간 − corr × c0 + 직전 상태 구간에서 pace 조건(gate, 처리 중 요청 보호) **하나 때문에** 불가였고 결국 pend 또는 reject된 요청들의 a ÷ E[L]) ÷ (판정선 − corr × c0).
- 갱신·진입 규칙은 KV 가격과 같다(진입값 = 1 ÷ 처리 중 요청의 남은 GPU 시간 최대값). 판정: λ × c + μ × a ≤ 1. 새 상수 없음.

**예측과 판정 규칙(실행 전)**:
- 표준 budget(KV가 한계): A와 차이 없음(모든 도착 ± 4.6, admitted ± 1) — 거절이 대부분 메모리 쪽이라 μ가 거의 0일 것. 반증: A보다 4.6점 넘게 낮으면 GPU 시간 가격이 KV가 한계인 조건에서 해를 끼친다.
- **절반 budget(토큰 간격이 한계, 결정적 시험, 2회)**: EXP-176 기록(PolyServe 74.88, v0.6 75.45, 후보 3 75.50; 세션 간 문턱) 대비 모든 도착 ≥ 78.9(PolyServe + 4),
  deepresearch 모든 도착 ≤ 60(지금 67~70), swe 모든 도착 ≥ 80(지금 72~76), token goodput은 v0.6 75.6k의 ± 5 %, admitted ≥ 99. 반증: 모든 도착 < 78.9이면
  "GPU 시간 가격이 요청 수를 정한다"는 통합 개념의 절반 budget 설명이 틀린 것이다.
- 의도적으로 포기하는 것: deepresearch(가치 1당 GPU 시간·KV를 가장 많이 쓰는 클래스)의 거절이 는다. 실패와 구분해 적는다.
