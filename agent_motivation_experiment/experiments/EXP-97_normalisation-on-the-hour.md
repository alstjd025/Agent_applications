# EXP-97 — 정규화를 고친 클래스 선호를 한 시간 믹스 이동 trace에서 잰다

**상태**: 끝남 (2026-08-25 04:10 KST, 4/4). 배포 바이너리 `c40896c` 판.
**정본**: 이 파일 §5·§6. 그림은 `results/aggregate_analysis/exp97_metric{,_b}/`.

## 1. 무엇을 묻나

EXP-96이 정적 도착률에서 잰 것을 **동적 경로**에서 다시 묻는다. 클래스 선호의 정렬 점수가
`w·share + (1−w)·room`이고 `share`가 **그 인스턴스 안에서 같은 tier가 차지하는 비율**이라,
100건 중 20건이 chat인 인스턴스(0.20)가 1건 중 1건이 chat인 인스턴스(1.00)보다 낮은 점수를
받는다. 즉 **모으려는 규칙이 오히려 비어 있는 인스턴스를 고른다.** 그것을 **그 인스턴스가 든
같은 클래스의 개수**로 바꾸면(`--fluidserve-affinity-metric=count`) 정렬이 의도대로 작동한다.

**정적 45 req/s에서는 고친 쪽이 3.3점 나빴다**(65.6 → 62.3, 메모리 탈락 10.0 → 17.8%).
그 결과가 **정적 포화 고유인지 동적 경로에서도 나오는지**가 이 실험의 질문이다. EXP-93이
"정적 45 req/s의 −7.1점은 동적에서 재현되지 않는다"를 한 번 겪었기 때문에 묻는다.

## 2. 설계

**trace**: `dyn60_shift_m2Am1B_b1045` — EXP-93이 만든 믹스 이동 stress trace. chat이
93.0 → 33.3 → 76.9 → 60.0%로 움직이고 도착률은 10.8~45.0 req/s.

**arm 셋** (대화·문서에서 부르는 이름 / 결과 디렉토리 / 세션):

| 부르는 이름 | 정렬이 무엇으로 순위를 매기나 | 디렉토리 | 세션 |
|---|---|---|---|
| **선호 끔** | 클래스 항이 아예 없다 (`room`만) | `fsnoaff` | EXP-93 |
| **지금 방식** | 그 인스턴스 안에서 같은 클래스가 차지하는 **비율** | `fspfx` | EXP-97 |
| **고친 방식** | 그 인스턴스가 든 같은 클래스의 **개수** | `fscount` | EXP-97 |

**두 FluidServe 변형이 같은 세션에 있으므로** 그 둘의 차분에서는 세션 오프셋이 상쇄된다
(통계에서 blocking). 선호 끔은 EXP-93 세션이고, **그 arm의 코드 경로를 이 바이너리가 건드리지
않으며** EXP-93이 같은 trace에서 2반복(폭 0.3)으로 쟀으므로 재측정하지 않았다.

**반복 2회씩, 총 4 run.** 주 지표는 **모든 도착이 분모, 거절은 위반**(`violate_offered`).

## 3. 사전에 적은 판정 규칙

- **확인**: 고친 방식이 총계에서 지금 방식보다 3점 이상 낮으면 "정렬을 고치면 나빠진다"가
  정적에 국한되지 않는다.
- **반증**: 3점 이내이면 정적 45 req/s의 −3.3은 정적 포화 고유다.
- **계측 검증**: 동률(`width≥2`)이 지금 방식보다 크게 줄어야 한다. 안 줄면 코드가 안 걸린 것이고
  성능 차이를 정렬 탓으로 읽으면 안 된다.

## 5. 결과

### 5.1 계측은 걸렸다 — 정렬 수정이 작동한다

run 전체에서 정렬이 어디서 결정하는지 (%, 반복 1 / 반복 2):

| | `width=0` (feasible 후보 없음) | `width=1` (점수가 유일하게 결정) | **동률 `width≥2`** |
|---|---|---|---|
| 지금 방식 | 67.5 / 65.6 | 27.9 / 30.0 | **4.59 / 4.36** |
| 고친 방식 | 70.1 / 71.6 | 29.8 / 28.4 | **0.09 / 0.04** |

**동률이 4.6%에서 0.05%로 사라진다.** 그만큼이 `width=1`로 옮겨 갔고, 최상위 인스턴스를
실제로 채택한 비율은 48.4/45.9 → 49.7/46.9로 거의 같다 — **동률이 채택으로 흡수됐다.**

**함대 배치에서도 확인된다.** 어느 인스턴스가 한 클래스를 가장 많이 드는지가 시간당 바뀌는 횟수:

| | chat | 세 클래스 평균 | chat을 든 적 있는 인스턴스 수 |
|---|---|---|---|
| 선호 끔 | 58.3 / 53.4 | 48.1 / 48.4 | 4 / 4 |
| 지금 방식 | 17.8 / 7.9 | 20.4 / 16.8 | 3 / 3 |
| **고친 방식** | **7.9 / 5.9** | **12.9 / 11.2** | **2 / 2** |

**고친 방식이 chat을 네 인스턴스 중 두 곳에만 놓고 시간당 5.9~7.9번만 옮긴다.**
선호 끔은 네 곳 전부에 놓고 53~58번 옮긴다. **정렬 수정은 의도한 일을 한다.**

### 5.2 그런데 총계가 6.1점 나쁘다 — 판정 규칙상 "확인"

전체 시간, 2반복, 모든 도착이 분모:

| | offered | admitted | 거절률 | token goodput | throughput |
|---|---|---|---|---|---|
| 선호 끔 (EXP-93) | 74.1 (폭 0.3) | 91.8 | 19.2% | 10,460 | 11,634 |
| **지금 방식** (EXP-97) | **75.0** (폭 0.2) | **93.1** | 19.4% | **10,654** | **11,749** |
| **고친 방식** (EXP-97) | **68.9** (폭 **4.2**) | 88.3 | 21.9% | 9,736 | 11,450 |

**고친 방식이 −6.1점이고 사전 문턱 3점을 넘는다.** 그리고 **반복 폭이 4.2로 다른 두 arm의
14~21배**다 — 결과 자체가 재현되지 않는다.

### 5.3 손실은 전 구간이 아니라 한 구간, 그 안에서도 마지막 10분이다

구간별 offered 달성률 (반복1/반복2 → 평균):

| 구간 | chat 비중 | 선호 끔 | 지금 방식 | 고친 방식 |
|---|---|---|---|---|
| s0 (m2) | 93.0% | 95.1/94.8 → 95.0 | 96.1/95.0 → 95.5 | 95.7/95.7 → **95.7** |
| s1 (균등) | 33.3% | 61.1/61.2 → 61.2 | 61.6/61.0 → 61.3 | 59.5/60.8 → 60.1 |
| s2 (m1) | 76.9% | 83.5/82.4 → 82.9 | 84.8/85.3 → 85.1 | 82.8/85.4 → 84.1 |
| **s3 (B)** | 60.0% | 58.4/60.4 → 59.4 | 59.4/61.0 → 60.2 | **34.6/46.1 → 40.3** |

**앞 세 구간에서는 셋이 1.2점 안에 있고, s3에서만 −19.9점이다.** 그리고 s3의 반복 폭이
**11.5점**(34.6 대 46.1)이라 그 구간 자체가 재현되지 않는다.

**그림이 위치를 더 좁힌다.** 클래스별 goodput 시계열에서 고친 방식의 chat이 **약 53~58분에만**
5,000에서 500 tok/s로 무너지고 나머지 시간은 세 곡선이 겹친다. 도착률 패널에서 그 구간이
**trace 전체의 최고 부하(35~46 req/s)**다. deepresearch와 swe에서는 오히려 고친 방식이 앞선다
(deepresearch 46~50분에 6,500 대 5,000).

## 6. 기제 — 두 판정 조건이 같은 양을 두 번 읽는 것이 정렬 수정에서도 그대로다

### 6.1 무엇이 깨지나: 토큰당 시간이다

s3 구간의 chat 요청 (예산 TTFT 5,000 ms, 토큰당 50 ms):

| | 수용 건수 | TTFT 초과 | **토큰당 초과** | TTFT p90 | **토큰당 p90** |
|---|---|---|---|---|---|
| 선호 끔 | 12,355 / 12,926 | 0.0% / 0.0% | 7.2% / 6.4% | 1,351 / 1,397 ms | 49.6 / 49.3 ms |
| 지금 방식 | 12,650 / 12,882 | 0.0% / 0.0% | 5.6% / 4.7% | 1,392 / 1,325 ms | 49.4 / 49.3 ms |
| **고친 방식** | 9,840 / 10,314 | 0.0% / 0.0% | **41.9% / 18.9%** | 1,409 / 1,700 ms | **53.2 / 51.2 ms** |

**첫 토큰은 세 arm 전부 예산 안이고, 깨지는 것은 토큰당 시간뿐이다.** 고친 방식만 p90이
예산 50 ms를 넘는다.

### 6.2 왜: 모으는 데 성공하면 그 인스턴스의 메모리가 찬다

인스턴스가 목적지로서 탈락한 사유 구성 (run 전체, %, 반복1/반복2):

| | 속도 게이트 | incumbents | **메모리(KV)** |
|---|---|---|---|
| 선호 끔 | 71.0 / 71.2 | 19.6 / 20.2 | **9.4 / 8.6** |
| 지금 방식 | 67.1 / 69.5 | 17.2 / 15.5 | **15.7 / 15.0** |
| **고친 방식** | **64.3 / 66.1** | 17.9 / 16.0 | **17.8 / 17.8** |

**세 arm이 모으는 세기 순서대로 단조롭게 늘어선다** — 모으는 힘이 셀수록 게이트 탈락이 줄고
(71 → 68 → 65%) 메모리 탈락이 는다(9.0 → 15.4 → 17.8%).

**이것이 EXP-93 §9.5가 측정한 거래와 같은 것이고, 정렬을 고치면 그 거래가 한 칸 더 진행된다.**
클래스가 모이면 chat이 빠진 인스턴스가 생겨 그 인스턴스의 허용 속도가 50 → 100 ms로 풀리고
(게이트 탈락 감소), 그 chat이 간 인스턴스에 토큰이 쌓여 메모리 탈락이 오른다. **두 조건이
같은 양 — 인스턴스가 지금 들고 있는 토큰 수 — 을 다르게 읽으므로, 함대가 들어야 하는 총
토큰 수가 워크로드로 정해져 있는 한 한쪽을 풀면 반드시 다른 쪽이 조인다.**

**그림이 그 토큰을 직접 보여준다**: 함대 KV 점유율 시계열에서 고친 방식이 48~60분에
**70~77.5%**로 가장 높고 지금 방식은 60~65%다. 같은 구간에서 고친 방식의 거절률이 50%까지
오르고(다른 둘은 42~44%), **admitted 달성률조차 40%로 떨어진다** — 더 거절하고도 받아들인
것을 못 지켰다.

### 6.3 chat 없는 인스턴스 비율의 두 값이 어긋난 것은 결함이 아니라 이 기제의 결과다

반복 1에서 클라이언트 기록 기반이 12.4%, 스케줄러 게이지가 42.5%로 30점 벌어졌고,
**반복 2에서는 36.2 대 36.6으로 일치한다.** 두 값은 원래 다른 양이다:

- 클라이언트 기반은 요청이 dispatch된 인스턴스에 **시작부터 종료까지 상주**한다고 본다.
- 스케줄러 게이지는 **남은 예산으로 더 이상 달성할 수 없게 된 요청을 게이트에서 뺀다.**

**반복 1이 바로 chat 토큰당 초과가 41.9%였던 run이고, 반복 2는 18.9%였다.** 즉 반복 1에서는
chat이 물리적으로 상주하는데 그 chat들이 이미 예산을 넘겨 스케줄러가 게이트에서 뺐고, 그래서
게이지만 "chat 없음"으로 읽혔다. **불일치의 크기가 예산 초과의 크기를 따라간다.**

## 7. 판정

**사전 규칙상 "확인"이다** — 정렬을 고치면 총계가 6.1점 나빠지고, 그것이 정적 45 req/s에
국한되지 않는다. **다만 손실의 성격이 정적과 다르다**: 정적에서는 −3.3점이 그 도착률 전체에
퍼져 있었는데, 여기서는 **한 시간 중 최고 부하 10분에 몰려 있고 재현되지 않는다**(반복 폭 11.5점).

**그래서 채택하지 않는다.** 배포 설정은 `share`(지금 방식) 그대로 둔다.

**⚠ 그러나 "정규화 결함은 없다"가 아니다.** 결함은 실재하고 고치면 정렬이 의도대로 작동한다
(동률 4.6% → 0.05%, chat을 든 인스턴스가 네 곳 → 두 곳, 시간당 교체 17.8 → 7.9회).
**바뀌지 않는 것은 총계이고, 나빠지는 것은 최고 부하 구간이다.** 지금 방식이 더 나은 것은
정렬이 옳아서가 아니라 **덜 모아서 메모리 한계를 덜 건드리기 때문이다.**

## 8. 인용할 때 같이 적어야 하는 것

- **선호 끔 arm은 EXP-93 세션이다.** 지금 방식과 고친 방식의 차이만 같은 세션에서 blocking된다.
- **고친 방식의 총계 반복 폭이 4.2점이다.** 다른 두 arm(0.2~0.3)과 같은 정밀도로 읽으면 안 된다.
- **s3의 −19.9점을 "구간의 성질"로 쓰면 안 된다** — 반복 사이에 34.6과 46.1로 갈린다.
- **`width=0`이 65~72%다.** 정렬이 결정하는 것은 나머지 3분의 1이고, 나머지는 feasible 후보가
  아예 없어 infeasible 중에서 고른 경우다. **정렬 규칙을 바꾸는 것의 영향 범위가 그만큼이다.**
- 이 trace는 **믹스 이동 폭이 Azure 근거를 넘는 stress test**이고 "현실적 워크로드"가 아니다.
