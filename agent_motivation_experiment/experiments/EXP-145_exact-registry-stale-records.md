## 0. 배경

EXP-144: 정확 장부(`--exact-residency`) run에서 장부의 처리 중 요청이 정답(보낸 뒤 마지막 토큰 전)보다 3분 이후 계속 100~145건(인스턴스당
13~92건, 장부의 9~27%) 많다. 그 기록들은 j가 계속 커져 p = 1로 outflow에 들어가, run 끝에는 인스턴스당 약 36만 토큰(KV 용량의 40% 남짓)을
곧 비워질 것으로 잘못 센다. 장부에서 기록이 빠지는 길은 하나다: 게이트웨이가 응답 끝에 `/complete`로 통지 → 스케줄러가 완료 표시(5분
tombstone) → FluidServe 장부가 다음 정리 때 그 표시를 보고 지운다. 어디서 빠지는지는 로그가 없어 가르지 못했다.

(나) 도착했는데 장부에서 지워지지 않아서인지(스케줄러 쪽).

## 11. 남는 기록이 생기는 조건 (2026-11-04, 기존 run 재분석)

용어: 이 기록부터 "옛 장부" = **inferred residency**(완료 알림 없이 엔진 running 수·생존확률로 처리 중 목록을 추정, 논문 구성),
"정확 장부" = **notified residency**(게이트웨이의 완료 통지로 목록에서 지움)로 부른다.

대시보드 스택 snapshot(파드 집합이 바뀔 때마다 기록)으로 각 run에서 이전 게이트웨이 파드가 사라진 시각을 찾아, 장부 초과(3~5분 평균,
클라이언트 기록 기준)와 맞췄다. 측정은 첫 요청 뒤 60초 warmup(1 req/s) 다음 35 req/s로 오른다.

| 이전 게이트웨이 파드가 사라진 시각 | run | 장부 초과 |
|---|---|---|
| +65~+76 s (부하가 오른 뒤) | EXP-141 r1~r3, EXP-142 br1~br3 중 9개, EXP-145 warmr1(밀림 있던 run) | +93 ~ +208 (예외 exp145smoker1 +69 s → +19) |
| +35~+57 s (부하가 오르기 전) | EXP-142 br3 `fsexactprogdl`, EXP-145 freshr1·freshbr1·warmbr1 | −9 ~ +0 |

- 장부 초과는 +70~+120 s 사이에 늘어나 고정된다(EXP-141 r1: +61 s −8 → +89 s +90 → +137 s +139). **게이트웨이 파드 교체가 부하 상승과 겹치면,
  사라지는 게이트웨이를 거친 요청들의 완료 통지가 오지 않는다.** 5절의 "게이트웨이가 오래 살아 있으면"은 틀렸고, 9·10절에서 재현되지 않은 것은
  엔진을 되돌리는 시간 때문에 이전 파드가 일찍 정리됐기 때문이다.
- 사라지는 게이트웨이가 왜 통지를 보내지 않는지는 미확인. 후보: 종료 신호 뒤 스케줄러 연결이 준비 안 됨이 되어 `NotifyComplete`가 조용히
  return(원래 바이너리는 로그 없음), 또는 통지를 보내는 goroutine이 프로세스와 함께 끊김.

## 13. 한 시간 run에서의 수명 (EXP-143 `fsexactprog`, 2026-11-04 재분석)

이전 게이트웨이 파드가 +69 s에 사라졌고, 장부 초과가 3~18분 +121~+131로 유지되다가 21분 +59, 24분 0이 됐다. 같은 때 20분 수명 규칙(`fsMaxRecordAgeMs`)으로
지운 기록이 30 → 131. 이후 60분까지 초과 −20~+1. **측정 시작의 게이트웨이 교체 때 생긴 약 125건이 20분 동안 남았다가 수명 규칙으로 지워졌다.**
남는 동안 j·KV가 커지므로 outflow 과대가 20분 직전에 가장 크다 — EXP-143에서 deepresearch 실패가 15~25분에 몰린 것과 시점이 맞는다.

해석(미확인 부분 표시): run 시작에 게이트웨이를 다시 띄우면 이전 파드가 종료 중에도 한동안 남고, 부하 생성기가 재사용하는 연결로 새 요청이 그 파드로
간다(미확인). 이전 파드는 요청을 정상 처리하지만 완료 통지가 스케줄러에 오지 않는다(왜인지 미확인). 그래서 엔진에서는 끝난 요청이 스케줄러의
처리 중 목록에만 남는다.

## 15. 게이트웨이 교체 smoke 결과와 정정 (2026-11-04 13:10~13:32, `261103_2019_exp145forcedr1_fsexactprog_t75_rpm_2100`)

- 교체 시점이 어긋났다: "첫 route" 검사가 이전 스케줄러의 카운터를 보고 즉시 통과해, 게이트웨이를 측정 시작 270초 **전**에 교체했다. 남는 기록 0건.
- **11·13절 정정**: "이전 게이트웨이 파드가 사라진 시각"으로 쓴 값은 실제로는 **스케줄러 파드 집합이 바뀐 시각**이다 — 대시보드 기록기는 스케줄러 파드가
  바뀔 때만 스택 snapshot을 남긴다. 표의 관계는 "스케줄러 파드 교체가 부하 상승(+60 s)을 넘겨 끝난 run(+65~+76 s)에서 남는 기록 +93~+208,
  그 전에 끝난 run(+35~+57 s)에서 0 안팎"으로 읽어야 한다.
- 새 단서: 게이트웨이 로그의 완료 통지 성공 줄 5,172개가 모두 `http://scheduler:8088/complete`(Service 이름)로 갔다. `/schedule`도 같은 HTTP 클라이언트로 같은
  주소를 쓴다(`scheduler_client.go` `doSchedule`). Service는 연결마다 파드를 고르고 클라이언트는 연결을 재사용하므로, 스케줄러 교체 중에는 일부 연결이
  이전 스케줄러 파드에 남는다.
- 가설(직접 확인 안 함): 새 스케줄러가 목록에 넣은 요청의 완료 통지가 이전 파드에 붙은 연결로 가면, 이전 파드가 200을 돌려줘 게이트웨이에 경고가 없고 새
  스케줄러는 통지를 받지 못한다. 이전 파드가 사라지면 연결이 새 파드로 다시 맺어져 그 뒤로는 정상 — 남는 기록이 측정 초반에 한 번 생기고 고정되는 것,
  게이트웨이 경고 0건, 스케줄러 교체 시각과의 관계가 모두 맞는다.
- 확인 방법: 측정 +55 s에 스케줄러를 다시 띄우고, 두 스케줄러 파드의 `/debug/fluidserve-registry`를 파드 IP로 직접 받아, 새 파드의 남는 기록 ID가 이전 파드의
  "받은 완료 통지"에 있는지 본다.
