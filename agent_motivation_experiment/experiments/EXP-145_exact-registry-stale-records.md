# EXP-145 — 정확 장부에 남는 기록은 완료 통지가 오지 않아서인가, 와도 지워지지 않아서인가 (smoke)

세션 접두어: `exp145smoke`

작성 2026-11-04, **실행 전**. EXP-144(분석 전용)의 R33 후속.

## 0. 배경

EXP-144: 정확 장부(`--exact-residency`) run에서 장부의 처리 중 요청이 정답(보낸 뒤 마지막 토큰 전)보다 3분 이후 계속 100~145건(인스턴스당
13~92건, 장부의 9~27%) 많다. 그 기록들은 j가 계속 커져 p = 1로 outflow에 들어가, run 끝에는 인스턴스당 약 36만 토큰(KV 용량의 40% 남짓)을
곧 비워질 것으로 잘못 센다. 장부에서 기록이 빠지는 길은 하나다: 게이트웨이가 응답 끝에 `/complete`로 통지 → 스케줄러가 완료 표시(5분
tombstone) → FluidServe 장부가 다음 정리 때 그 표시를 보고 지운다. 어디서 빠지는지는 로그가 없어 가르지 못했다.

## 1. 무엇을 묻나

남는 기록이 (가) 통지가 스케줄러에 도착하지 않아서인지(게이트웨이 쪽: `NotifyComplete`가 조건에 걸려 조용히 return, 두 번 전송 실패),
(나) 도착했는데 장부에서 지워지지 않아서인지(스케줄러 쪽).

## 2. 방법

- arm `fsexactprog`(정확 장부 + 엔진 대기 요청 제외, EXP-142와 같은 구성·바이너리: 스케줄러 `3251836a`, 게이트웨이 `590242b0`), 35 req/s, 6분.
  드라이버 `k8s/exp07/run_exp142_progress.sh onerep`(바꾸지 않음).
- run 동안 따로 받아 두는 로그(`/home/nxclab/scratch/exp145/`): 스케줄러 전체 로그 중 `complete notice`(스케줄러가 받은 통지마다 V(4)로 한 줄),
  `dispatch request`, 경고·오류 줄. 게이트웨이 로그 중 경고·오류 줄과 `complete notice`(전송 실패 시 경고). 둘 다 파드가 바뀌면 새 파드에 다시 붙는다.
- 끝난 뒤: route된 요청 ID 집합 R, 스케줄러가 통지를 받은 ID 집합 C, 클라이언트 기록의 마지막 토큰 시각으로 시각별
  "끝났는데 통지를 받지 못한 요청 수" = |{끝남} − C| 를 장부 초과분(대시보드 기록의 `live_requests` − 정답)과 비교한다.

## 3. 판정 규칙 (실행 전 고정)

- 끝난 요청 중 통지를 받지 못한 수가 장부 초과분의 80% 이상을 설명하면 **(가) 통지 미도착**. 게이트웨이 경고 줄로 어느 조건인지 본다.
- 거의 모든 끝난 요청의 통지를 받았는데(미수신 ≤ 장부 초과분의 20%) 장부 초과분이 그대로면 **(나) 스케줄러 쪽**.
- 둘 다 아니면(장부 초과분이 이번에는 생기지 않음 등) 그대로 적고 판정하지 않는다.
- smoke이므로 점수는 판정에 쓰지 않는다.
