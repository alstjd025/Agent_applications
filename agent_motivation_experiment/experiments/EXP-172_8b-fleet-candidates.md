## A1: v0.6 + 클래스별 인스턴스 상한 끄기 (`fsxnocap`, 플래그만, 스케줄러 `7dc2355c`)

**판정 (2회, v0.6 EXP-170 r1·r2와 지표마다)**:

- 같이 적는 것: preemption(같은 세션끼리만), 엔진 KV ≥ 0.973 비율, `instcap_sole_block_total`이 0인지(꺼졌다는 확인), 인스턴스별 클래스 구성.

## 후보 2: 이미 약속한 일에 대한 KV 판정 + 실측 오차로 정한 여유 (`fsxc2`, 상한 끔, 스케줄러 `774156a5`)

**이론**: 측정 기반 admission control(Jamin et al. 1995, Grossglauser–Tse 1997) — 지금 있는 흐름과 새 흐름 하나만으로 판정하고, 여유는 측정한 오차의 분위수로 둔다. 바깥 저장소 브랜치 `exp172-cand2-mbac`(0badf89·3e274a3), 플래그 `--fluidserve-kv-epsilon`(기본 0 = v0.6), 설계 노트 `/home/nxclab/scratch/exp172/cand2/notes.md`.

**메커니즘**: 인스턴스마다 이미 약속한 KV — max(엔진 논리 KV + 대기·보냈지만 아직 엔진 보고에 없는 prefill, 스케줄러 기록의 살아 있는 요청 prompt + 생성 토큰 합) — 에서 출발해, 처리 중인 요청의 성장과 클래스 길이 분포로 기대한 종료를 τ = 0~512 iteration 격자에서 따라가고 **그 최댓값**(끝점이 아니라)에 이 요청을 더한 것을 `pool × (1 − m)`와 비교한다. pool은 물리 KV 전체(여유 1.0), m은 그 인스턴스가 지난 512개 예측에서 낸 오차(실현된 최댓값 − 예측 최댓값, 그 사이 새로 보낸 요청은 뺀다)의 (1−ε) 분위수. **사라지는 상수**: 메모리 여유 0.95, outflow 하한 z = 1.65, 메모리 판정의 h = 100, 그리고 상한을 끄므로 상한의 창 배수 3.0과 내부 상수들. **생기는 것**: ε 하나(5 %). pace 판정·첫 토큰 판정은 v0.6 그대로라 요청의 ladder 여유를 쓰는 판정은 늘지 않는다.

**오프라인 추정(결정은 v0.6 그대로 둔 상태, 4 run)**: ε 5 %에서 여유 8B 3.8~4.0 %·70B 2.3~2.4 %(pool 대비 중앙값), 표본 밖 초과율 5.5~6.5 % — 같은 ε에서 함대마다 여유가 다르게 나온다. v0.6이 고른 인스턴스에서 판정이 바뀌는 route 8B 68 %(그중 chat의 79~83 %는 같은 초에 다른 인스턴스가 통과), 70B 섞인 trace 8~9 %(전부 다른 인스턴스가 통과 → 배치만 바뀜). 정적 계산이라 시스템이 어디로 수렴할지는 run만 보여 준다.

**판정 (2회, EXP-170 v0.6·PolyServe와 세션 간 문턱, A1과는 같은 세션)**:
- 아홉 지표와 goodput 각각. 목표: 모든 도착이 PolyServe(73.48)와 "차이 없음" 이상이고 v0.6보다 높음.
- **반증 조건**(설계 에이전트가 실행 전에 적은 것): ① preemption이 A1 대비 50 % 넘게 줄지 않으면 판정이 결과(preemption)를 제어하지 못한 것; ② preemption은 줄었는데 모든 도착이 A1보다 4점 넘게 낮고 거절이 늘면 EXP-114 §13.42의 재현; ③ 실측 초과율(gauge `kv_margin_frac`·`committed_peak_tokens`)이 ε 5 %에서 2~10 % 밖이면 ε가 보정되지 않은 것.
- **예상**(에이전트): preemption −70 % 이상, admitted ≥ 98.5, 모든 도착 68~74, chat ≥ 72, swe 55~68, deepresearch 64~71(KV를 많이 쓰는 클래스라 정직하게 거절되어 내려감), goodput +2~7 %. PolyServe를 문턱 넘게 이기리라고는 예상하지 않는다.
- 70B 확인(시간이 되면): 섞인 trace에서 어느 지표도 v0.6(EXP-161)보다 문턱 넘게 나쁘지 않을 것.

## 후보 3: 인스턴스별 KV 가격 (`fsxc3`, 상한 끔, 스케줄러 `5d52124e`)

**이론**: 네트워크 효용 최대화의 쌍대 분해(Kelly 1998; Low–Lapsley 1999 — TCP 혼잡 제어를 가격 알고리즘으로 본다), 온라인 primal–dual packing. 브랜치 `exp172-cand3-price`(b18bf3b), 플래그 `--fluidserve-kv-price=off|shadow|on`(기본 off = v0.6), 노트 `/home/nxclab/scratch/exp172/cand3/notes.md`.

**메커니즘**: 인스턴스마다 가격 λ(KV·토큰·step당 가치). 부족도 u = (사용 중 물리 KV + 아직 계산하지 않은 prefill 토큰) ÷ 물리 pool — u > 1은 vLLM이 preemption하거나 prompt를 대기시키는 조건이다. 엔진 상태가 새로 올 때마다 λ ← λ·exp((u−1)·Δt/H), H = h × 그 인스턴스의 실측 step 시간(한 계획 구간 동안 가격의 상대 변화 = 상대 부족도; 조정할 이득 상수가 없다). u가 처음 1을 넘으면 λ를 "처리 중 요청 가운데 남은 수명 비용이 가장 큰 것"의 역수로 놓고, 그 아래로 내려가면 0(묶이지 않은 제약은 가격이 0). 요청 비용 c_r = (prefix 적중을 뺀 prompt) × E[L] + E[L²]/2 (클래스 길이 분포, 논문 식 (1)). 판정: v0.6 판정에 더해 λ·c_r ≤ 1(가치 = 요청 하나당 1, 채점 지표와 같다); 같은 affinity 점수끼리는 λ·c가 낮은 인스턴스를 먼저. 클래스 가중치는 없다 — 비싼 요청부터 거절되고, 그것이 어느 클래스인지는 비용이 정한다. 사라지는 것: 상한의 창 배수 3.0과 상한 내부 상수. 생기는 조정값: 없음(h는 이미 있음). 메모리 여유 0.95는 이 arm에서 그대로.

**오프라인 추정(1차 닫힌 루프, 4 run)**: u > 1이 preemption을 예측한다(preemption의 81~93 %가 u > 1인 초에, 99 %가 그 5초 안). 가격이 거절하는 도착: 8B deepresearch 5.1~5.3 %(그 클래스에서 비용이 큰 쪽, 중앙값 8.2M 대 클래스 중앙값 3.6M KV·토큰·step), chat·swe 0.03~0.07 %; 70B deepresearch 0.35~0.46 %. 점수 이득 상한은 느슨하다(8B +9~+10점, 70B +1점; 처리량·pace 한계를 무시).

**판정 (2회)**:
- 아홉 지표와 goodput 각각, EXP-170 v0.6·PolyServe와 세션 간 문턱, A1과는 같은 세션.
- **반증 조건**(실행 전): R1 preemption이 50 % 넘게 줄지 않거나 부족 시간 비율(gauge `kv_shortage` > 1)이 줄지 않음 → 가격이 루프를 닫지 못함; R2 preemption은 줄었는데 chat·swe 모든 도착이 A1보다 문턱 넘게 오르지 않음 → 그들을 막은 것은 부족이 아니었음; R3 deepresearch 모든 도착 −8점 초과, 또는 모든 도착이 A1 이하 → 비용 기준 배분이 손해; R4 70B 섞인 trace에서 어느 지표든 문턱 넘게 나쁨; R5 가격 거절(`kv_price_decisions_total{outcome=sole_block}`)의 10 % 넘게 chat.
- **예상**(에이전트): 모든 도착 +6~+12, admitted ≥ 98, chat +8~+18, swe +10~+30, deepresearch −6~+3, goodput +3~10 %, preemption ≤ 15k/run, A1 대비 +2~+6.

## 후보 1: 인스턴스별 AIMD KV 창 (`fsxc1`, 상한 끔, 스케줄러 `49459912`)

**이론**: TCP 혼잡 제어 — Chiu–Jain AIMD(곱셈 감소·덧셈 증가는 β∈(0,1)이면 효율적인 운전점으로 수렴하고 β·W*와 W* 사이를 오간다), Reno/NewReno 복구, RFC 5681(FlightSize에서 자른다), RFC 7661(창을 실제로 썼을 때만 늘린다). 브랜치 `exp172-cand1-aimd`(f9d41cf·73fcba6), 플래그 `--fluidserve-kv-window`, `--fluidserve-kv-window-beta`, `--fluidserve-kv-window-signal`(기본 끔 = v0.6), 노트 `/home/nxclab/scratch/exp172/cand1/notes.md`.

**메커니즘**: 인스턴스마다 창 W(메모리 판정이 받아들이는 물리 pool의 비율; 0.95 고정값 자리에 들어가고 0.95는 시작값만 된다). 손실 신호 = 스케줄러가 직접 보는 preemption("실행 중이던 요청이 엔진 대기열로 돌아왔다"; 엔진 상태에 대기 요청 id 목록이 0.5초마다 온다). 손실이면 W ← 0.7 × min(W, 판정이 본 점유율), 그 뒤 처리 중이던 요청 수만큼 완료될 때까지(한 바퀴) 추가 손실은 무시. 손실이 없고 창이 실제로 후보를 거절한 적이 있으면 완료마다 (요청 하나의 KV ÷ pool) ÷ 처리 중 요청 수만큼 증가(한 바퀴에 요청 하나만큼). 상한 1.0, 하한 요청 하나의 KV. 조정값: 0.95(고정 여유) → β 0.7(CUBIC 표준값). h·z는 그대로.

**오프라인 추정(정적)**: 8B는 8대 모두에서 창이 결정에 개입(v0.6 route의 68 %가 정착한 창 위에서 이루어졌다), 70B 섞인 trace는 chat 엔진은 손실이 없어 그대로이고 deepresearch·swe 엔진만 개입(route의 10 %). **위험**: 70B에서 deepresearch 엔진의 KV를 0.95에서 약 0.81로 낮춰 deepresearch 모든 도착이 −2~−8 나빠질 수 있다(70B에서는 KV가 처리량을 올리고 preemption 비용이 작다). 창 붕괴(연속 손실로 하한까지 내려감)도 위험.

**판정 (2회)**: 아홉 지표와 goodput 각각, EXP-170 기록과 세션 간 문턱, A1과 같은 세션. **반증 조건**(실행 전): 8B 모든 도착이 v0.6보다 4점 넘게 낮음, goodput −5 % 초과, 또는 `kv_window` gauge가 0.2 아래에 시간의 5 % 넘게 머묾(붕괴). **예상**(에이전트): 엔진 KV ≥ 0.973 시간 < 10 %, ITL ≤ 35 ms, admitted ≥ 98, 모든 도착 64~69(혼자서는 PolyServe 격차를 닫지 못함), chat +0~+6, deepresearch −0~−6.
