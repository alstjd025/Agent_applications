# EXP-34 — fluidic KV 투영이 결정의 몇 %를 바꾸는가

**상태**: 2026-07-29 완료
**바이너리**: `staging/scheduler-exp07-v29fluxcount` (`md5 cbbefe34`)
**선행**: [fluidserve-implementation.md §28.5](../../../ms_dev/notes/fluidserve-implementation.md)

---

## 1. 왜 이걸 재는가

이 프로젝트의 출발점은 KV를 흐름으로 모델링하는 것이다. §28.5에서 그 기여를 계산했다:
투영과 스냅샷의 차이 48,501 토큰 × `c_kv = 1.41151e-5` = **0.68 ms**, 예측 반복시간
46 ms 중.

계산은 "작다"고 말하지만, 게이트가 45.0이고 예측이 46.4인 상황에서 0.68 ms는 결정을
뒤집을 수 있는 크기이기도 하다. **얼마나 자주 뒤집는지는 워크로드의 성질이고 계산으로
나오지 않는다.**

## 2. 왜 A/B가 아니라 세는가

`--fluidserve-flux=false`가 이미 있어 ablation arm을 돌릴 수 있다. 그렇게 하지 않은
이유가 둘이다.

**① 효과가 산포보다 작을 것이다.** 80 req/s의 attainment 산포는 3 run에서 84.0~90.0,
즉 6점이다. 0.68 ms가 몇 점을 만드는지 모르는 채로 6점 잡음 속에서 읽게 된다.

**② 되먹임이 결과를 삼킨다.** flux를 끄면 예측이 올라가고 → 배치가 줄고 → 엔진이
가벼워지고 → 실측 반복시간이 내려가고 → **보정계수가 따라 내려가 예측을 다시 내린다.**
v25가 정확히 이 고리에서 판정 불능이 됐다(duty를 0.163→0.110으로 내렸는데 보정계수가
1.022→1.091로 올라 예측이 제자리).

그래서 **같은 run, 같은 상태, 같은 순간에 두 판정을 나란히 계산해 다른 횟수를 센다.**
되먹임을 안 타고, 반복도 필요 없다.

```go
newKv    := f.proj + cost           // 지금
snapKv   := f.kvLogical + cost      // 그림자
feasible != snapFeasible  →  카운트
```

세 레벨을 따로 센다. 후보 하나가 뒤집히는 것과 요청의 운명이 바뀌는 것은 다르다.

| 레벨 | 무엇 |
|---|---|
| candidate | 인스턴스 하나의 feasible이 뒤집힘 |
| **decision** | **배치되느냐 보유되느냐가 갈림 — 클라이언트가 보는 것** |
| target | 배치는 되는데 목적지가 다름 |

## 3. 판정 규칙 (실행 전에 적었다)

| decision 레벨 | 결론 |
|---|---|
| **< 1%** | 투영이 여기서 결정하지 않는다. A/B에 2시간 쓰지 않고 워크로드를 바꾼다 |
| **> 10%** | 자주 결정한다. A/B가 값어치 있다 |
| 1~10% | 60 req/s에서만 A/B (거기 산포는 0.05점) |

## 4. 결과

| rate | 레벨 | 뒤집힘 | 평가 | 비율 |
|---|---|---|---|---|
| **60 req/s** | candidate | 9,330 | 558,500 | 1.671% |
| | **decision** | 2,740 | 139,625 | **1.962%** |
| | target | 1,498 | 139,625 | 1.073% |
| **80 req/s** | candidate | 4,050 | 985,236 | 0.411% |
| | **decision** | 1,770 | 246,309 | **0.719%** |
| | target | 412 | 246,309 | 0.167% |

**80 req/s에서 0.72%, 60 req/s에서 1.96%.**

### 4.1 부하가 높을수록 영향이 줄어든다 — 예상과 반대다

1.96% → 0.72%. 포화에 가까울수록 게이트 근처에 결정이 몰릴 것이라 예상했으나 반대다.

§28.5와 일관된 설명이 있다. 80 req/s에서는 결정의 85%가 PEND이고, 그것은 **예측이
게이트보다 한참 위**라는 뜻이다. 0.68 ms를 더하든 빼든 여전히 위다. 60 req/s는 예측이
게이트를 오가므로 뒤집힘이 더 자주 생긴다.

**투영이 의미를 가지려면 예측이 게이트 근처에 있어야 하는데, 이 워크로드는 그 구간을
빨리 지나간다.**

### 4.2 계산과 실측이 일치한다

| | |
|---|---|
| 계산 (§28.5) | 투영의 예측 기여 **0.68 ms** / 46 ms |
| 실측 (이 실험) | 투영이 결정을 바꾸는 비율 **0.72~1.96%** |

**출발점인 fluidic KV 모델이 이 워크로드에서 결정의 1% 안팎만 바꾼다.** 죽어 있지는
않다 — 1,770~2,740번은 실제로 바꿨다 — 그러나 결과를 좌우하지 못한다.

원인은 KV가 쌓이지 않는 것이다. 출력이 249~523 토큰이라 지평 100 스텝 안에 요청이
계속 끝나고, `outflow`가 커서 `proj ≈ kvLogical`이 된다.

## 5. 판정과 다음

**규칙대로 A/B ablation은 하지 않는다.** 80은 기준 아래고 60도 1% 대다.

이 숫자를 **기준선으로 고정**하고 워크로드를 바꾼다.

```
deepresearch 출력 249 토큰 :  투영이 결정의 0.72~1.96% 를 바꿈   ← 지금
deepresearch 출력 2,500    :  투영이 결정의     ?% 를 바꿈       ← 다음
```

이 두 값의 차이가 **"핵심 메커니즘이 이 워크로드에서는 놀고 있었고 저 워크로드에서는
일한다"**의 직접 근거가 된다. A/B였다면 6점 산포에 묻혔을 값을 20분에 얻었다.

**변경 방법은 프롬프트다.** `ignore_eos`로 길이를 강제하는 안은 접었다 — 출력 길이의
변동은 LLM 실험의 본질이고(같은 입력이 run마다 34% 다른 길이를 낸다, CLAUDE.md 참조),
없애면 `expectedOutflow`의 `z·√(...)` 항이 무의미해져 오히려 양쪽 다 쉬워진다.
에이전트가 출력 양식을 입력으로 주는 방식이 자연스러운 통제 수단이다.
