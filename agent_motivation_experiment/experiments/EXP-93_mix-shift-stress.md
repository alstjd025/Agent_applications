# EXP-93 — 믹스가 균등 구간을 통과하는 stress trace: 믹스 이동은 시스템이 고르지 않은 용량 변화다

**작성 2026-08-23, 실행 전.** 사용자 지시로 "(나) 믹스가 균등 구간을 통과하는 한 시간 trace"를
건다. 비교 arm은 FluidServe v0.2(`fspfx`)와 llm-d(`llmdslo`), 2반복, 총 4 run 약 5시간.

## 1. 왜 이 실험이 필요한가

심사 반문 중 **"workload distribution shift에 robust한가"**에 대한 지금 답은
`paper_evaluation_2026-08/13_robustness_map.md`이고, 그 근거의 동적 부분은 배포된 한 시간
trace(`dyn60_short_m123_b1045`) 하나다. **그 trace에서 chat이 요청의 66.7~93.0% 사이에서만
움직이고 균등(33.3%) 영역에 한 번도 가지 않는다.** 그래서 지금 쓸 수 있는 문장은
"chat 다수 안에서 믹스가 이동해도 견딘다"까지이고, 리뷰어가 묻는 distribution shift의 폭을
덮지 못한다.

이 실험이 새로 묻는 것은 그 폭만이 아니다. **믹스가 움직이면 도착률이 그대로여도 시스템이
초당 감당할 수 있는 요청 수가 바뀐다.** 우리 워크로드에서 클래스별 평균 입력 길이가
chat 674 / deepresearch 4,055 / swe 6,812 토큰으로 열 배 차이가 나므로, 요청 개수 비율이
바뀌면 **요청 하나의 무게가 바뀌고 무릎(90% 달성률을 유지하는 최대 도착률)이 같이 움직인다.**
도착률은 그 변화를 전혀 알려주지 않는다. **이것이 라우팅 계층이 적응해야 하고 고정 배정이
못 하는 것의 가장 직접적인 형태이며, 아직 아무도 재지 않았다.**

## 2. 무엇을 바꿨나 — 믹스 일정 하나뿐이다

새 trace `traces/dynamic/canonical/dyn60_shift_m2Am1B_b1045.csv`.
생성 인자가 배포된 한 시간 trace와 **seed(20260726)·도착률 대역(10~45 req/s)·Azure 원본
구간·구간 길이(900초)·warmup(60초)까지 전부 같고 `--mix-schedule`만 다르다.**

**검증 완료 (실행 전)**: 두 CSV의 `arrival_s` 열이 99,242행 **전부 동일**하고, `class` 열만
46,632행(47.0%)이 다르다.

```
m123 (배포된 것)  m1 → m2 → m3 → m1     chat 76.9 → 93.0 → 66.7 → 76.9 %
shift (이번 것)   m2 → A  → m1 → B      chat 93.0 → 33.3 → 76.9 → 60.0 %
```

**단조 하강이 아니라 큰 하강 → 큰 상승 → 중간 하강**으로 잡았다. 단조로 만들면 "믹스가
무거워진 것"과 "시간이 흘러 밀린 요청이 쌓인 것"이 구분되지 않고, 되돌아오는 구간이 없으면
**회복하는지**를 못 본다.

## 3. 구간별 상태 — 이 표가 실험의 설계다

무릎 추정은 **m1의 측정된 무릎 28.0 req/s(EXP-80, 8 도착률 2반복)를 요청당 입력 토큰 수에
반비례로 환산한 것**이다. 균등 믹스에 대해 이 방법이 12.1을 주는데, EXP-92의 두 점(15 req/s
83.3~85.0, 20 req/s 71.3~73.7 offered)에서 외삽한 12.5와 맞으므로 환산법이 대략 맞는다.
**m2·B의 무릎은 측정된 적이 없는 추정치다.**

| 구간 | 믹스 (요청 개수 기준) | 입력 토큰 기준 | 요청당 입력 | 도착률 p5/중앙/p95 | 무릎 추정 | 구간 중 무릎 위 |
|---|---|---|---|---|---|---|
| s0 | m2 — chat 93.0 / dr 4.7 / swe 2.3% | 64.4 / 19.4 / 16.2% | 974 | 10.7 / **23.6** / 41.6 | ≈48 | **0%** |
| s1 | **A — 33.3 / 33.3 / 33.3%** | 5.8 / 35.1 / 59.0% | **3,847** | 14.0 / **24.7** / 38.7 | **≈12** | **100%** |
| s2 | m1 — 76.9 / 15.4 / 7.7% | 31.1 / 37.5 / 31.4% | 1,666 | 13.9 / 27.4 / 38.7 | **28.0** (측정) | 48% |
| s3 | B — 60.0 / 30.0 / 10.0% | 17.6 / 52.8 / 29.6% | 2,302 | 16.7 / 35.8 / 44.6 | ≈20 | 88% |

> **s0과 s1의 도착률 중앙값이 23.6 대 24.7로 4.7% 차이인데 무릎 대비 위치는 0% 대 100%로
> 정반대다.** 같은 도착률이 한 구간에서는 무릎의 절반이고 다음 구간에서는 두 배다. **이 짝이
> 이 실험의 핵심 측정이고, 같은 run 안에 있으므로 세션 효과가 원리적으로 들어올 수 없다.**

⚠ **"균등"한 것은 요청 개수이지 토큰이 아니다.** s1에서 입력 토큰의 59.0%가 swe이고 chat은
5.8%다. 요청당 입력이 974 → 3,847 토큰으로 **3.95배**가 된다. 배포된 trace의 같은 값은
1,666 → 974 → 2,413 → 1,666으로 범위가 2.48배이므로, **이 trace는 요청 무게의 이동 폭을
2.48배에서 3.95배로 넓힌다.**

## 4. 가설과 반증 조건 — 실행 전에 확정한다

주 지표는 **요청 단위 offered 달성률**(모든 도착이 분모, 거절은 위반)이고, 그 옆에 admitted,
거절률, token goodput을 항상 같이 낸다.

### H1 (핵심, run 안에서 닫힌다) — 같은 도착률에서 구간 사이 차이가 구간 안 도착률 효과보다 크다

s0과 s1의 **겹치는 도착률 구간(약 14~39 req/s)에서 같은 도착률 bin끼리** FluidServe의 달성률을
비교한다.

- **확인**: 겹치는 bin 전부에서 s1이 s0보다 낮고, **평균 차이가 20점 이상**.
- **반증**: 평균 차이가 **8점 미만**이거나 부호가 bin마다 뒤집힌다. 그러면 "믹스가 용량을
  바꾼다"는 주장을 이 데이터로 못 한다.
- 8~20점이면 구별은 되나 약하다고 적는다.

**세션 효과가 들어올 수 없다** — 두 구간이 같은 run의 서로 다른 15분이다.

### H2 — 전환 직후의 비용이 llm-d에서 더 크다

각 구간 경계 앞 3분과 뒤 3분의 달성률 차이를 arm별로 낸다. 경계는 셋
(m2→A 하강, A→m1 상승, m1→B 하강).

- **확인**: **m2→A 경계에서 llm-d의 하락이 FluidServe보다 5점 이상 크다.**
- **반증**: FluidServe의 하락이 llm-d보다 5점 이상 크다.
- ⚠ 전환 3분 창에는 도착률 자신의 변화도 섞이는데, **생성기가 구간 경계를 도착률 봉우리와
  일부러 어긋나게 두므로** 두 arm이 같은 도착률 변화를 겪는다. arm 사이 차분에서 상쇄된다.

### H3 (부차, 세션을 건너간다) — 넓힌 믹스 이동이 우리 우위를 줄이지 않는다

배포된 한 시간 trace에서 EXP-71이 잰 값은 FluidServe 81.0(폭 1.5) 대 llm-d 56.7(폭 1.8),
**격차 +24.3**이다.

- **확인**: 이 trace에서도 격차 **20점 이상**.
- **반증**: 격차 **12점 이하** — 믹스 이동 폭을 넓히면 우리 우위가 절반이 된다는 뜻이고,
  robustness 주장을 그만큼 좁혀 적어야 한다.
- ⚠ **이것은 세션을 건너가는 비교다.** EXP-71은 2026-08-09, 바이너리 `a96dac12`,
  게이트웨이 `GOMAXPROCS` 미설정. 지금은 `89d9593b`(추가된 플래그의 기본값이 false라 동작
  동일)와 `GOMAXPROCS=16`(EXP-82가 달성률·거절률·goodput은 반복 폭 안에서 안 움직인다고
  확인). **그래도 H1·H2를 주 근거로 쓰고 H3은 보조로 쓴다.**

## 6. 알려진 한계 — 고치지 않고 기록한다

1. **s1에서 swe의 prefix 재사용이 부풀려진다.** transcript가 1,500건인데 s1에서 swe가 도착의
   3분의 1이라 **사본 간격이 약 2.7분**이고, 스케줄러 prefix 색인의 보유 시간(약 2.8분)
   안이다. m1 구간에서는 9.1분이라 안전하다. **두 arm이 같은 trace를 보지만 prefix 재사용을
   쓰는 방법이 다르므로(우리는 인스턴스별 prefill 청구, llm-d는 cache-aware 점수), s1의
   수치를 prefix 동작의 깨끗한 비교로 읽으면 안 된다.** transcript 확대는 별도 미결 과제이고
   지금 하면 더 나쁜 문제(13,218건 판은 구조적 prefix 공유가 98.9%)로 바뀐다.
2. **믹스 이동 폭이 Azure가 뒷받침하는 범위를 넘는다.** Azure 2024의 conv/code 비 이동이
   4.71배이고 배포 trace의 swe 입력 토큰 비중 이동이 4.07배인데, 이 trace는 요청 무게 기준
   3.95배이면서 chat 비중을 93%에서 33%로 옮긴다. **논문에서 "현실적 trace"가 아니라
   "의도적으로 범위를 넓힌 stress test"라고 이름을 붙여야 한다.**
3. **llm-d에 예열 주행을 주지 않는다** — EXP-71과 같다. trace의 도착률이 움직여서 예열할
   고정 도착률이 없다. trace 자신의 60초 warmup 구간에서, 그리고 측정 중에 예측기가 학습한다.
4. m2와 B의 무릎은 **추정치**다(측정된 것은 m1의 28.0뿐).
