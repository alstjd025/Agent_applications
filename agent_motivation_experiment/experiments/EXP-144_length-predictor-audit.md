# EXP-144 — 출력 길이 예측(생존함수)은 얼마나 맞고, outflow 예측의 오차는 어디서 오나 (분석 전용)

## 0. 배경

FluidServe는 처리 중인 요청 r마다 클래스별 출력 길이 생존함수 S(·)(`deploy/profiling/llama31-70b-b200-tp2/fluidserve.json`,
2026-08-02 8월 run들로 만든 것)로 "다음 h = 100 step 안에 끝날 확률" p = (S(j) − S(j+h)) / S(j)를 구하고, outflow =
Σ p·(prompt + j) − 1.65·√Σ p(1−p)(prompt + j)²를 KV 판정에 쓴다(`fluidserve.go` `expectedOutflow`). 같은 S로 기대 남은 토큰 수
E[L − j | L > j]를 구해 허용 속도에 쓴다. j는 관측하지 않고 "보낸 뒤 step 수 − prefill step 수(− 엔진 대기 step 수)"로 추정한다.

2026-11-03 측정(`/home/nxclab/scratch/predacc/predacc.py`, 2초 표본, 실제 = 100 step을 관측 step 시간으로 바꾼 시간 안에 끝난 요청의
prompt + 출력): outflow 예측/실제가 논문 구성 0.68~0.81, 정확 장부 2.38~2.64, 정확 장부 + 엔진 대기 요청 제외 1.67~3.05.
이 비율에는 z 하한, 장부, j 추정, 생존함수, KV 크기 정의, 시간 변환이 섞여 있다.

## 1. 무엇을 묻나

- **Q1** 생존함수 자체는 얼마나 맞는가. 실제 j를 넣었을 때 "h step 안에 끝날 확률"의 calibration(예측 구간별 실제 비율), 기대 남은
  토큰 수의 편향(클래스·j 구간별), 프로파일 분포와 run의 실제 길이 분포(분위수)의 차이.
- **Q2** outflow 예측의 과대·과소가 어느 요소에서 오는가. 기록된 예측에서 한 요소씩 정답으로 바꿔 다시 계산한다:
  z → 0, 장부 → 실제 처리 중 집합, 추정 j → 실제 j, 생존함수 → 실제 남은 길이. 각 단계의 변화가 그 요소의 몫이다.
- **Q3** 논문 구성의 결과는 horizon 덕분인가 우연한 상쇄인가. Q2 분해에서 요소들의 방향, 그리고 h = 50·100·200에서 같은 분해.

## 2. 방법과 정답 데이터

- 대상: Q1은 EXP-141·142·143의 run 29개 전부(정책과 무관한 워크로드 성질), Q2·Q3는 FluidServe 계열 17개(대시보드 기록이 있음).
- 실제 j(t) = `tbt_events.jsonl`에서 시각 t까지 받은 토큰 수. 실제 처리 중 집합 = dispatch 로그의 인스턴스·시각부터 마지막 토큰까지.
- step 시계: 인스턴스마다 decode 중인 요청들이 1초에 받은 토큰 수의 중앙값을 누적한다(decode step마다 토큰이 하나씩 나온다).
  "h step 안" = 이 시계로 h step.
- 추정 j는 같은 step 시계로 `step(t) − step(보낸 시각) − ceil(prompt / 8192)`를 다시 계산한다. 옛 장부는 같은 규칙(생존확률 0.02,
  20분, running 수에 맞춰 j가 큰 것부터)을 오프라인으로 다시 적용해 재현한다. **재현이 기록된 예측과 맞는지를 먼저 확인하고**(아래
  판정 규칙), 맞지 않으면 그 run의 분해는 보고하지 않는다.
- 엔진 대기 요청 제외 run은 대기 step을 정답 데이터로 다시 만들 수 없으므로, 그 run에서는 Q1과 "실제 j로 바꾼 단계"까지만 보고한다.

## 3. 판정 규칙 (분석 전 고정)

- 재현 신뢰도: 오프라인으로 다시 계산한 "추정 j + 장부 + z" outflow가 기록값과 바쁜 표본 합계 기준 ±15% 안이어야 그 run의 분해를 쓴다.
- Q1 "생존함수가 맞다": 실제 j를 넣은 outflow 평균(z = 0)이 실제(prompt + j 기준)의 0.9~1.1배이고, calibration 구간별 차이가
  0.05 이하. 벗어나면 그 방향과 클래스를 적는다.
- Q3 "우연한 상쇄": 논문 구성에서 두 요소 이상의 몫이 서로 반대 방향이고 각각 ±20%를 넘는데 순 오차는 그보다 작으면 상쇄로 본다.
  h를 바꿨을 때 j 요소의 몫이 h에 반비례해 줄면 "horizon이 j 오차를 덮는다"로 본다.

### 정확 장부의 남는 기록 — 과대 예측의 대부분
- 장부의 처리 중 요청 수가 정답(보낸 뒤 마지막 토큰 전)보다 **3분 이후 계속 약 100~145건 많다**(EXP-141 r1 `fsexact`: 장부 941·988·963
  대 정답 802·848·813). 엔진 running + waiting도 정답과 같은 쪽이다. 모든 route가 클라이언트 기록과 맞으므로 정답 집합에 빠진 요청은 없다.
- 남는 기록의 수는 일정한데 기록값과 재현값의 차이(A − B, 네 인스턴스 합)는 시간이 갈수록 커진다: 2분 5.9만 → 8분 145만 토큰
  (`fsexactprog` 5.1만 → 104만). 같은 기록이 지워지지 않고 남아 j가 계속 커지고, 생존확률이 0이 되어 p = 1, KV(prompt + j)도 커지는 모양이다.
- 확인: "측정 초반에 끝난 요청 중 인스턴스마다 남는 수만큼이 영원히 장부에 남는다"고 두고 재현하면 분 단위 비율이 기록값과 같은 모양으로
  오른다(EXP-141 r1: 기록 1.00·0.96·1.25·1.45·1.95·2.97·5.28, 재현 0.65·1.03·0.97·1.14·1.22·1.79·3.22). 크기는 약 2/3까지 재현된다.
  "끝난 뒤 Δ초 늦게 지워진다"(Δ = 1~10 s)는 기록값을 재현하지 못했다(10 s에서도 1.45 대 2.21).
- **원인은 아직 모른다.** 게이트웨이가 완료 통지를 보내지 못한 경우(`NotifyComplete`가 조용히 return하는 조건, 두 번의 시도 실패) 또는
  스케줄러 쪽 처리 중 하나인데, 게이트웨이 로그가 run 디렉토리에 남지 않아 이 데이터로는 가를 수 없다. 한 시간 trace(EXP-143)에서
  deepresearch가 15~25분에 실패한 것은 남는 기록의 j·KV가 20분 수명 한도에 가까워질 때까지 커진 것과 시점이 맞는다(확인 안 함).

### Q3 horizon인가 우연한 상쇄인가 — 둘 다 아니고 z다
- 논문 구성에서 생존함수(−3%), j 추정(+2.6%), 옛 장부(+4.5%)는 각각 작고 서로 상쇄하지도 않는다. 규칙의 "두 요소 이상이 ±20%를 넘고 반대
  방향"에 해당하지 않으므로 **우연한 상쇄가 아니다.** 순 0.75배는 거의 전부 z = 1.65 하한(−28%)에서 온다 — 설계된 보수성이다.
- h = 50·100·200: E 0.973·0.971·0.974, D 1.000·0.997·0.997 — 생존함수와 j 요소는 h에 거의 무관하다(**horizon이 j 오차를 덮는 것이 아니다**,
  j 오차가 처음부터 작다). h에 따라 바뀌는 것은 z의 몫이다(B 0.63·0.75·0.81): h가 짧을수록 끝날 요청의 기댓값이 작아 상대 표준편차가 커진다.

### R32 정정
EXP-141 r1 분석(R32)은 "옛 장부의 count-trim이 j 과대 계산을 상쇄했다"고 적었다. 이번 분해로는 **처리 중인 요청의 j 과대는 논문 구성에서
+2.6%로 작고**, 정확 장부에서 outflow를 2~3배로 만든 것은 **엔진에 없는데 장부에 남은 기록**이다. 옛 장부의 count-trim(엔진 running 수에
맞춰 지움)은 그런 기록을 지우는 효과가 있었다. 엔진 대기열 요청의 j 과대(+15%)는 실재하고 엔진 대기 요청 제외로 고쳐졌다.
